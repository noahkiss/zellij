# v0.45.1-nkmk.23

- **Upstream base:** unchanged — the `v0.45.1` release tag (`efd8fd5a8`), plus the one commit
  taken ahead of the next base in nkmk.22
- **Range:** `v0.45.1-nkmk.22..main`
- **Released:** 2026-09-28

Five patches, and every one of them is about a report that said the wrong thing while looking
right. Two came out of the nkmk.22 rollout the same afternoon: doctor called a stale server current
after `session enable` had refreshed the pin under it, and the RC proof was found to be able to
write the candidate over the live pin. One is a field the consumer keys on, `terminal_command`,
naming a command that had exited. One is a signing fall that could re-key every TCC grant to
another team without a word. The last is the MCP help text, which counted the tools and was off by
one. Nothing here crosses a contract, and no field is added anywhere.

## Fixed

### A refreshed pin is no longer mistaken for the build the server is running

```
$ zellij session enable mysession        # refreshes the pinned copy to the new build
$ zellij session doctor mysession
# before
  build     the running server is this build of zellij        # it was not
# after
Needs you
  build     'mysession' runs a different build from this binary
```

**The check asked the right process and read the wrong file.** It resolves the server's executable
by pid, which is right, and then reads the build off the file that path now holds. `session enable`
renames the new build onto that path under a live server, so from that moment the path holds a
build the server is not running, and doctor compared the new pin with itself. Linux escaped by
accident, because `/proc/<pid>/exe` grows a " (deleted)" suffix; macOS reports the path and says
nothing. Seen on two rollouts.

**The session's socket is the reference time.** The server binds it as it comes up and nothing
writes it again, so an executable modified after the socket was bound is not the file the process
started from. `server_executable` now asks that one `stat` question and, when the answer is yes,
discards what it read off the file and sets the `replaced` flag Linux already set. Everything
downstream is unchanged: `compare_builds` says `Different`, `ls --json` carries
`server_exe_replaced: true`, the stderr warning fires, and doctor owes a restart. A socket or
executable that cannot be read leaves the identity as it was, because a false "stale" sends someone
to restart a session that was fine.

### A pane that dropped to the shell stops naming the command that exited

```
$ zellij action list-panes --all --json | jq '.[] | {handle, terminal_command, is_held, exited}'
{"handle":"sunny-otter","terminal_command":"sh -c npm test","is_held":false,"exited":false}  # before
{"handle":"sunny-otter","is_held":false,"exited":false}                                      # after
```

The pty swapped the dead command for the default shell and nothing told the pane, so
`terminal_command` still named the command the pane was opened with. `Tab` now records the drop at
both sites that send `DropToShellInPane`, the ESC handler and the clean-exit path, and the field
goes absent, which is what an ordinary shell pane carries. The snapshot already recorded `None`
here; the live report now agrees with it. `command_state` was considered and is not a substitute:
it is absent for a shell that emits no OSC 133, which is exactly the consumer's fallback case.

### A fall to another team's certificate is refused instead of dropping every grant

```
signing  Needs you   <pin> holds grants recorded against team A1B2C3D4E5, and the certificate
                     below belongs to team Z9Y8X7W6V5
                       ...sign with a certificate of the granted team, or re-grant the
                       permissions for the pin's path once another one is in place
```

The fall from a Developer ID to an Apple Development certificate is safe because both write the
same designated requirement, and that holds only while both carry one team. Nothing checked. A
keychain with a personal and an employer's certificate could fall to the other team's OU, write a
requirement macOS never recorded, and every grant against the old one stopped applying while
`codesign --verify` reported a valid signature. `judge_fall` now reads the granted team out of the
requirement the pin is anchored on and refuses a rung from another team, leaving the pin and its
grants as they were. An unsigned pin and a rung whose team cannot be read keep their pass, on
purpose: the first has no grant to lose and the second would block the commonest unreadable
keychain on no evidence. Known limitation since nkmk.7; a check now.

### The MCP help text stops counting the tools

`zellij mcp --help` said seven; eight have been served since nkmk.21. The client reads the list
from the server, so the text now says what the tools are for and not how many there are.

## Changed

### A release candidate never becomes the pin

```
$ zellij session up mysession        # from a candidate, with the rc formula linked
warning: <pin> was left alone: this build is a release candidate (0.45.1-nkmk.23-rc.1),
         and the pin is the build a restart comes back on.
```

AGENTS.md says an RC tag is proof, never an install target. The pin did not know: its one writer
asks only whether the build in hand differs from the pin, and a candidate certainly does, so proving
one copied it onto the path a restart comes back on. The nkmk.22 proof got as far as `codesign`
refusing before a locked keychain, and only that stopped it. `install_pinned_exe` now refuses any
build whose version carries `-rc.`, once per pin per process, after the staleness checks and before
the signing guard. An interactive launch from a candidate serves the session from the candidate,
not the pin, so a proof still proves the candidate. `session enable` refuses when it would write a
unit naming a pin that does not exist.

## Operator notes

- **Doctor's `build` line can be trusted again after `session enable`.** A rollout that refreshes
  the pin under a running server now reads "runs a different build" until the restart. `ls --json`
  says the same in `server_exe_replaced`.
- **A candidate on `PATH` no longer reaches the pin.** Any unreleased local build still does; the
  guard is `-rc.` in the version and nothing else.
- **A consumer reading `terminal_command`** gets an absent field for a pane at its prompt, whether
  it never ran a command or dropped back to the shell after one.
- **Nothing crosses a contract.** `PaneInfo` and `PaneListEntry` keep their fields, and
  `server_exe_replaced` on `ls --json` is the field that already existed for the Linux case. No
  protobuf, no client/server contract, no config key.
