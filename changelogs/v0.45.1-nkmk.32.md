# v0.45.1-nkmk.32

- **Upstream base:** unchanged — the `v0.45.1` release tag (`efd8fd5a8`), plus the one commit
  taken ahead of the next base in nkmk.22
- **Range:** `v0.45.1-nkmk.31..main`
- **Released:** 2026-10-11

A script can now wait for a pane's shell to be ready before it types: `action wait --for ready`,
and `--wait-ready` on every verb that makes a pane. The MCP `zellij_create` uses it to run its
command inside a ready interactive shell by default, so the user's rc files, aliases and `PATH`
apply. `OSC 9;4` progress from the focused pane reaches the terminal. Three fixes ride along: a
restored agent pane holds only its bare resume, `session enable` keeps the recorded `PATH`
directories a shell lacks, and `trz`/`tsz` behind `tssh` no longer start a second transfer.
Nothing crosses a contract.

## Added

### `action wait --for ready`

```
$ zellij action wait sunny-otter --for ready
waited_ms: 212
ready_by: prompt
```

It answers when the pane's shell has finished its rc files and drawn a prompt. Two signals, and
the exact one wins:

| `ready_by` | signal |
|---|---|
| `prompt` | the shell's OSC 133 prompt marker: `command_state: prompt` in `list-panes` |
| `quiet` | the pane drew a non-blank line, then nothing for `--quiet-ms` (300 by default here) |

- A running command is never ready by quiet, however long it is silent.
- A missing `command_state` keeps both signals in play. A clear resets a pane's markers, so a
  shell that writes them reads as having none until its next prompt.
- The timeout is 10 seconds by default. A pane that closes or exits first is a miss, exit 2.

### `--wait-ready` on the verbs that make a pane

```
$ zellij action new-pane --wait-ready
pane_id: terminal_4
handle: sunny-otter
ready_by: prompt
ready_ms: 252
```

`action new-pane`, `run`, `action edit`, `edit` and `action new-tab` take it. The client runs the
`--for ready` wait on the pane it made and adds `ready_by` and `ready_ms` to the report.
`--ready-timeout <SECONDS>` bounds the wait, 10 by default.

- A pane that is not ready in time is still reported, so the caller can close it. The reason goes
  to stderr and the exit is 2.
- `--wait-ready` is refused beside `--blocking` and `--block-until-exit*`.
- The client holds the flag, like `--handle`. It never reaches the action or the contract.
- `action --json` carries both fields.

### `zellij_create` types its command into a ready interactive shell

`$SHELL -c` is non-interactive, so a command from the MCP tool missed the `.zshrc`, its aliases
and `mise activate`. Two new parameters, and the default is the new behaviour:

| parameter | default | effect |
|---|---|---|
| `run_in` | `shell` | `shell` makes a shell pane with `--wait-ready`, then types `command` and presses Enter. `exec` keeps the old `$SHELL -c` command pane. |
| `wait_ready` | `true` | the readiness wait in `shell` mode; `false` types at once |

- A readiness timeout types nothing. The result is `reason: not_ready`, `ready: false`,
  `input_sent: false`, with the pane's `pane_id` and `handle`.
- A ready create carries `ready`, `ready_by` and `ready_ms`.
- The per-tool parameter cap rises from eight to nine to fit the two.

### `OSC 9;4` progress reaches the terminal, for the pane you are looking at

```
$ printf '\e]9;4;3\a'; sleep 5; printf '\e]9;4;0\a'   # Ghostty draws its bar, then clears it
```

Claude Code reports progress with ConEmu's `OSC 9;4`, and Ghostty, Windows Terminal and ConEmu
draw it as a bar. Upstream dropped it. Now each pane keeps its last report, and after each render
every client gets the report of the pane it has focused:

- every new report from the focused pane, a repeat included, so a host keeps the bar alive;
- the new pane's report, or `9;4;0`, when focus moves to another pane or tab;
- a clear when the pane's program exits.

A client is sent a clear only over a bar it was sent, because some terminals show any `OSC 9` as
a desktop notification. The report rides the render output; the contract is unchanged.

## Fixed

### A restored agent pane holds only the bare resume

A pane launched as `claude --model opus --dangerously-skip-permissions '<prompt>'` came back as
the same line plus `--resume <id>`. Enter would have resumed the session and sent the prompt again
as a new turn.

A known harness is now recorded as argv0 plus its session words only:

| what named the session | recorded |
|---|---|
| the live session | `claude --resume <id>`, `codex resume <id>`, `opencode --session <id>`, `pi --session <id>` |
| an id in the argv, nothing live | the same form, with the argv's id |
| nothing | the picker: `claude --resume`, `codex resume`, `pi --resume`, bare `opencode` |
| a configured hint | argv0 and the hint's words |

Launch flags such as `--model` are dropped with the prompt. A hint for an unknown command still
only appends. The prefill types the bare resume of whatever a snapshot holds, so a snapshot
written before nkmk.32 does not type its old prompt either.

### `session enable` keeps the recorded `PATH` directories a shell lacks

The nkmk.27 rule kept the installed unit's `PATH` only when the enabling shell added nothing. A
dotfile change put mise's shims on every shell's `PATH`, so the next `enable` over SSH rewrote one
Mac's agent `PATH` from 20 entries to 14, and dropped seven that exist.

Now `enable` merges. A shell that adds nothing keeps the recorded `PATH` in its own order. A shell
that adds a directory is written first, followed by each recorded directory it lacks that still
exists. fnm's per-shell `fnm_multishells` directory is never kept. A configured `PATH` is still
written as stated. The `enable` message names the kept directories.

### `trz` and `tsz` work through zellij behind `tssh`

trzsz starts a transfer with a plain-text trigger that zellij keeps on the grid, so every redraw
of that row sent it to `tssh` again. The second transfer failed and typed `#fail:...` into the
shell (trzsz-ssh issue #135). zellij now does the rewrite the trzsz relay does under tmux: a
trigger id ending `00` is stored ending `20`, which the client starts once. A trigger split across
two pty reads is not rewritten; `trz` writes it in one call.

## CI and release process

- **Dependabot opens no pull requests.** Upstream's `.github/dependabot.yml` is kept with
  `open-pull-requests-limit: 0` on every entry. Dependencies move when the base moves.

## Operator notes

- **The prompt signal needs OSC 133 from the shell.** Without a `precmd` hook that prints
  `\e]133;A\a`, every answer is `quiet`.
- **An MCP caller that needs a command's exit status passes `run_in: exec`.** The default shell
  pane stays a shell when the command ends.
- **`enable` keeps only what the unit records.** A directory an earlier `enable` already dropped
  is not in the unit, so it comes back only from a shell that has it.
- **Nothing crosses a contract.** A restart picks the changes up.
