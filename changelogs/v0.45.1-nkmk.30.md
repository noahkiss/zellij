# v0.45.1-nkmk.30

- **Upstream base:** unchanged — the `v0.45.1` release tag (`efd8fd5a8`), plus the one commit
  taken ahead of the next base in nkmk.22
- **Range:** `v0.45.1-nkmk.29..main`
- **Released:** 2026-10-06

CI now signs and notarizes the macOS binary with the fork's Developer ID. A pin refresh installs
that signed build as it came, and the per-Mac signing ladder is gone: nothing on a Mac signs the
pin any more, and an upgrade never needs the login keychain. Each Mac owes one re-grant when its
pin first switches to the release signature. Two smaller fixes ride along: the
live pane list reports a command pane as its own command, and doctor's `path` line compares
builds, not paths. Nothing crosses a contract; no `ls --json` field changes shape.

## Added

### CI signs and notarizes the macOS binary

The `aarch64-apple-darwin` leg of `release.yml` signs the binary as
`Developer ID Application: NKMK Digital Co. (2Z88BYP37C)`, identifier `org.zellij.nkmk`, with the
hardened runtime and a timestamp. It submits the binary to Apple's notary service and fails unless
the verdict is `Accepted`. The tarball's name and layout do not change. A bare binary cannot be
stapled, so Gatekeeper fetches the ticket online.

RC tags are signed the same way, so a candidate proved on a Mac carries the real signature. The
secrets live in the Actions environment `release`, which admits `v*` tags only. To rebuild a tag,
dispatch the workflow **on the tag** (`--ref v<version>`); a dispatch from `main` fails the macOS
leg.

### A release build is pinned with its own Developer ID, and nothing re-signs it

A pin refresh re-signed every new build with a local rung: Apple Development on one Mac, the
minted certificate on another. That threw away the release signature and needed the login
keychain, which SSH leaves locked.

Now a refresh first checks whether the new build is the release's own. The build must verify
against an anchored requirement, name `org.zellij.nkmk` and team `2Z88BYP37C`, and satisfy the
Developer ID intermediate and leaf markers. A build that passes is copied into place as it came,
verified again and renamed. Nothing runs `codesign -s` or `security`, and no password is read.

`session up`, `session enable` and doctor's `pin` line say "refreshed the pinned copy with the
release's own signature at <pin>". Doctor's signing finding says what happened:

```
Changed
  signing   refreshed <pin> with the build's own Developer ID signature; nothing was signed here
```

### The per-Mac signing ladder is gone; a release is signed once, in CI

Nothing on a Mac signs the pin any more. A release build carries the fork's Developer ID and is
pinned as it arrived. Any other build, such as a local `cargo build` or a source-formula build,
is a plain copy over an unsigned pin. Doctor then reports "not a release build, so the pin holds
no grants" and says to install the brew release. Over a signed pin such a build is refused, and
the signed pin stays on the previous build.

The Apple Development and minted-certificate rungs are removed, with certificate minting and
backup and all keychain handling, `ZELLIJ_KEYCHAIN_PASSWORD` included. A pin still anchored on a
retired rung is left alone until the next release refreshes it. That switch records the one owed
re-grant, and doctor names it: "an earlier run switched this pin to the release's Developer ID
requirement". `--no-sign` now means "leave a signed pin as it is"; `--sign` is still accepted and
does nothing.

## Fixed

### `list-panes` and `list-agents` report a command pane as its own command

nkmk.29 fixed serialization. The live pane list still asked every pane the shell question, so a
command pane was listed as its newest child: an MCP server, a tool shell, a `sleep`. A layout
`command "claude"` pane then got no `AGENT_ID`. The live list now makes the same split
serialization makes: a command or editor pane is asked about its own process. Shell panes are
unchanged.

### Doctor's `path` line compares builds, not paths

`check_path` called any other file first on `PATH` "a DIFFERENT build". Doctor run from the pin
always finds the package's binary first: another file, the same build. The line now asks
`compare_builds`, as the `pin` line does, and reports "the same build as this binary".

## Operator notes

- **Each Mac owes one re-grant.** A pin anchored on Apple Development or on the minted
  certificate does not match the release signature. So the first refresh to a signed release
  writes `signing/regrant-owed`, and doctor reports "two things left" under `Needs you`. Do not
  restart until the operator re-grants Full Disk Access for the pin path at the keyboard and runs
  `zellij session doctor --fix --regranted <session>`. Later releases owe nothing.
- **No keychain unlock, ever.** A release build is installed as-is and nothing else is signed, so
  `doctor --fix` reads no password and needs no unlocked keychain. A local or source build is not
  pinned over a signed pin; install the brew release instead.
- **Nothing crosses a contract.** No config key, no subcommand, no `ls --json` change. A restart
  picks the pane fixes up.
