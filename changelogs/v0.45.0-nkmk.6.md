# v0.45.0-nkmk.6

- **Upstream base:** `f42ca3c79` on upstream `main` (workspace version `0.45.0`) — unchanged since
  nkmk.1
- **Range:** `1f3f7a735..main` (129 commits)
- **Released:** 2026-08-15

One theme, and it is the CLI. Every command the fork touches now answers in one of three shapes,
every pane carries a two-word address a human can type, a verb that changes nothing says so with a
distinct exit code, and anything that cannot be undone asks first. `zellij action --help` groups
eighty-seven verbs into five bands and states those rules once; `setup --dump-surface` prints the
whole tree, flags and outputs included, in one call. Around that: `zellij session doctor` checks in
one pass everything that has to hold for a session to come up and stay up, `zellij mcp` serves seven
tools over the Model Context Protocol, `list-agents` says which panes are running a coding agent,
and the two full-width notices the server used to composite over the viewport become one badge
beside the clock. Underneath, `Layout::pane_count` stops counting a layout's template twice, which
lets a session be clean for the first time — and that, in turn, needed a fingerprint so a clean
session still records a renamed pane.

This is the widest CLI change the fork has made. **Scripts written against nkmk.5 need edits**; see
[For consumers](#for-consumers) at the end.

## Added

### One output convention, and the commands that moved to it

Reading one command now teaches you how to read the next.

- **A single record is `key: value` lines**, the key in `snake_case`. `new-pane` answers `pane_id:
  terminal_7` and `handle: sunny-otter`, not a bare number.
- **A list of like things is a table** with an `UPPER_SNAKE` header row.
- **A nesting of like things is an outline.** Only `list-tree` has anything to nest.
- **All three are append-only.** A key or a column may be added in any release; none is renamed or
  removed, and a name means the same thing in every command that prints it.
- **Results to stdout, diagnostics to stderr.** A payload command prints the payload and nothing
  else.

A mutation reports what it changed rather than acknowledging that it ran: `close-pane` prints
`closed: terminal_3`, `move-tab` prints `from:` and `to:`, `go-to-tab` prints the tab it left and
the tab it landed on. The answer is usable — a script that moved a tab knows where to move it back.

`list-panes`, `list-tabs` and `list-clients` print every column always, rather than gating fields
behind flags; `list-clients` gains `TTY`, `SIZE` and `CURRENT`, which were reachable only through
`--json`. `zellij ls` is a table. `dump-screen` takes its path as an argument as well as `--path`.
`query-tab-names` is gone — `list-tabs` answers it and answers more.

### Exit codes: `0` acted, `1` error, `2` the command changed nothing

The `2` is one bucket with several doors: a **miss** (a well-formed request about something that is
not there), a **refusal** by one of the three target classes below, a **confirm** nothing could
answer or that you declined, a **wait** that timed out, and a call clap would not accept. A `1` is
narrower — the call could not be carried out at all: a regex that does not compile, a handle a live
pane already holds, text too large or not UTF-8, a server that failed.

**The sentence on stderr, not the exit code, says which door it came through.** The branch had
drifted three ways before this: the targetless guard refused with `1` while the confirm layer beside
it declined with `2`, `setup --json` with no question exited `1` where clap's own usage error exits
`2`, and FORK.md claimed both numbers in two different sections.

### Pane handles: a two-word address a human can type

```
zellij action go-to-pane sunny-otter
zellij action dump-screen --pane-id sunny-otter
```

Every pane carries a handle — `sunny-otter` — assigned at creation and unique among the session's
live panes. Every `--pane-id` takes one, alongside `terminal_1`, a bare integer and a pane uuid; one
parser serves all four forms. It is drawn at the right of the pane's title row, in both frame
styles, and it appears in the `HANDLE` column of `list-panes`, the `handle:` key of every creation
command, the `list-tree` outline and both halves of a `go-to-pane` report.

**It survives a restore and the uuid does not.** The handle is the pane's address and is serialized
into the snapshot; the uuid is its *lineage* and rotates, because a restored pane is a new process
(`restored_from` links it to the old one). It is reused after the pane closes — uniqueness is over
live panes only, so a handle written down last week names at most one pane today, and not
necessarily the same one.

`switch-session --pane-id` is the one flag that names a pane in a *different* session, and it takes
the id forms only. A handle read against the session you are leaving would land on whatever pane
wears that number in the session you are joining, so it is refused with exit 1 rather than answered
wrongly.

#### Choosing one

```
zellij action new-pane --handle build -- cargo watch
zellij run --handle build -- cargo watch
zellij edit --handle notes notes.md
```
```kdl
layout {
    pane handle="build" command="cargo" { args "watch" }
}
```

A generated handle is memorable but not predictable, so a script has to read the id out of the
report and carry it. A chosen handle is the other way round: the caller decides the address before
the pane exists, and every later command already knows it. Every command that reports the pane it
made takes it, on the same terms.

The grammar is up to four lowercase words joined by dashes, each at most 16 characters, at most 40
in all, at least one letter. That is what keeps one `--pane-id` able to take four forms — and a name
whose first word is `terminal` or `plugin` is refused too, because `terminal-1` beside `terminal_1`
is a name that gets typed wrong on the day it matters. A handle a live pane already holds is an
error, exit 1, checked before the pane is made.

A chosen handle survives the trip to the server, which is what makes `new-tab --layout` and `zellij
--layout` honour a `handle` a layout wrote: the client/server contract carries `pane_handle`
alongside the pane's other declared properties. In a layout, `handle` is the spelling a person
writes and `pane_handle` is what serialization writes; both reach the same field.

`launch-plugin` and `launch-or-focus-plugin` are the exception and print nothing at all: a plugin's
pane is built on the plugin thread after the action was answered, so nothing comes back carrying an
id. The surface map used to promise `pane_id:` and `handle:` for both; the promise is removed rather
than the reader being taught a report that never arrives. `zellij plugin` goes through the
pane-creating path instead and takes `--handle`.

### What a verb does when you do not tell it what to act on

A `zellij action` client is attached to nothing, so "the focused pane" resolves against whichever
client the server can find. From inside a pane that is right and is the point. From a script it is a
pane the caller has never seen. So the verbs are in three classes:

| Class | With no target | Verbs |
|---|---|---|
| 1 | Works anywhere | focus movement, the scroll family, the toggles, `switch-mode`, and every creating verb |
| 2 | The focused thing, inside the session only | `rename-pane`, `rename-tab`, `edit-scrollback`, `resize`, `move-pane`, `move-tab`, the `break-pane` family, `clear` |
| 3 | Refused: name it | `close-pane`, `close-tab`, `write`, `write-chars`, `send-keys`, `paste` |

**Class 3 always names its target, from inside too** — that is what moved. Run from inside a pane,
"the focused pane" is the shell that ran the command: a targetless `write-chars` types into the very
shell you typed it in, and a targetless `close-pane` closes it. Nobody means either. **`--focused`**
(or `--current`) is how to say you did, and it is valid only where a focus exists — from a script it
is refused, naming `--pane-id`, because there are no hands there to mean it.

Class 2 from a script exits 2 and names the `--pane-id` or `--tab-id` that answers it.
`break-pane-right` and `break-pane-left` cannot name a target at all, so from outside they are
refused outright. None of this governs keybindings: a key is pressed by somebody looking at the
thing it acts on.

### Anything that cannot be undone asks first

```
$ zellij action close-pane --pane-id build
close-pane kills whatever is running in that pane. Are you sure? [y/N]

$ zellij action close-pane --pane-id build < /dev/null
`close-pane` kills whatever is running in that pane, and cannot be undone. Nothing here can answer
a prompt, so pass `--yes` to say you meant it.
```

One rule, one implementation, one wording. On a terminal it asks, defaulting to no. Anywhere else —
a pipe, a cron job, an agent — it refuses and names `--yes`. A script must never meet a prompt it
cannot answer: a command that blocks forever waiting for a keypress nobody is there to press is
worse than either answer. A refusal and a declined prompt both exit 2.

It covers `close-pane`, `close-tab`, `clear`, `kill-session`, `delete-session`, `snapshot rm` and
`snapshot prune`. `kill-all-sessions` and `delete-all-sessions` already prompted and now do it
through the same helper. What deliberately does not confirm: `signal-pane` (the signal's name is the
stated intent), `session down` (the fork snapshots first, so it is recoverable), the write family
(class-3 targeting is the guard it needs), and `dump-screen --path` over an existing file (a
`read`-band verb, and every tool that takes an output path behaves this way).

### `zellij action --help` groups the verbs, and `setup --dump-surface` prints the whole tree

```
zellij setup --dump-surface          # the outline convention
zellij setup --dump-surface --json   # the same map, structured
```

Every command in the tree with its band, its one-liner, its aliases, and each flag's type, default
and help — then what clap cannot know: what the command prints, and the keys or columns it prints
under.

```
command: zellij action list-tree  group: read
  about: List every tab with its panes nested beneath it
  prints: outline  keys: tab_id position name active / handle pane_id title command focused
  arg: --json  type: flag  about: Output as JSON
```

A command with no `prints:` line prints nothing when it succeeds; that is the fork's default rather
than a gap, and the dump's header says so. Only the bands and the `prints:` table are written down —
everything else is read out of the same clap tree that parses the call, and a test walks a command's
arguments out of clap and requires each one by name. A flag added tomorrow is in the map tomorrow.
The dump runs before the configuration is read, like `--dump-config` beside it: a broken config must
not take the map away.

`zellij action --help` is the same information for a reader. It opens with the conventions above and
then lists the verbs in five bands — `read`, `navigate`, `create`, `mutate`, `session` — rather than
one alphabetical column of eighty-seven. The listing is built from the command tree, so a command
cannot appear in it saying something its own `--help` does not, and a command nobody put in a band
fails the build.

Every subcommand's `--help` was swept against one test: an agent reading only this text uses the
command correctly. Two failures are worth naming. `--tab-id` is the **stable** tab id — the `TAB_ID`
column of `list-tabs` — while `go-to-tab` takes the 1-based display position, and sixteen commands
said only "Target a specific tab by ID". And `new-pane --block-until-exit` prints no `pane_id:` at
all: the exit status is the answer, and a caller parsing for the id would wait for a line that never
comes. The blocking flags are not one thing — `--block-until-exit` waits for the **command**, bare
`-b/--blocking` waits for the **pane**, and a pane whose command ended is held open by default.

### Where a new pane goes: `--new-tab`, `--near`, `--in-tab`

```
zellij action new-pane --new-tab build -- cargo test    # a tab of its own, made now
zellij action new-pane --near sunny-otter -- htop       # beside that pane, wherever it lives
zellij action new-pane --in-tab logs -- tail -f app.log # into that tab, without going there
```

`new-pane` placed a pane beside the focused one, or in the tab `--tab-id` named. Three flags say it
without needing the focus to be anywhere in particular, which is what a script has.

**`--new-tab [NAME]`** makes the tab and puts the pane in it, reporting `tab_id:`, `pane_id:` and
`handle:`. The command is handed to the new tab as its first pane, so this is one action and not
two, and the tab is built from the session's own new-tab template — it keeps its status bars and its
panes are written into the saved layout. It is the one placement flag that moves the focus, the way
`new-tab` itself does; `--no-focus` says otherwise. `--name` and `--borderless` are refused rather
than dropped, because the first pane of a new tab is described by its command and nothing else.

**`--near <pane>`** takes any pane target and opens beside it, in whatever tab it lives in. It is
`--near-current-pane` generalised: that flag anchors to `$ZELLIJ_PANE_ID`, which is no answer at all
from a script. The anchor must be a terminal pane, because the message carries a terminal id; a
plugin pane is refused rather than quietly placed somewhere else.

**`--in-tab <name-or-id>`** puts the pane in a tab that already exists. All digits is read as the
stable `TAB_ID`, anything else as a name, both looked up in the same `list-tabs` answer. Neither
`--near` nor `--in-tab` moves anybody's focus — a script that puts a pane in another tab has not
asked to be taken there, and a `zellij action` client that "focuses" something is moving a focus
that belongs to somebody else.

### `wait`: blocking on a pane instead of polling it

```
$ zellij action wait build --for exit
waited_ms: 41207
exit_status: 0
```

The command a script writes instead of `send-keys`, `sleep 2`, `dump-screen`, look, `sleep 2` again.
That loop is what every wrapper around this fork was writing, and it is wrong in both directions at
once: too slow when the thing finished immediately, and too quick when it did not.

Three conditions: **`--for exit`** (the command ends; prints `exit_status:`), **`--for quiet`** (the
pane produces nothing for `--quiet-ms`, 500 by default), and **`--for match --match <regex>`** (a
line the pane delivers matches).

**The exit code is about the wait, not about the command.** Met is 0 whatever `exit_status` says; a
timeout is 2; a regex that does not compile is 1. Deliberately unlike `new-pane --block-until-exit`,
which exits with the command's own status — that one made the pane and owns it, while `wait` is a
question about somebody else's, and a script has to tell "the tests failed" from "I never saw them
finish". `--timeout` is 300 seconds unless you say otherwise, and `--timeout 0` waits forever.

What `--for match` can see: it matches the **rendered screen** line by line, not the byte stream, so
a wrapped line arrives as two and a pattern spanning the wrap matches neither half. Lines already on
screen when the wait began are the baseline. A line identical to one already on screen is not new —
each render carries the whole viewport rather than a delta.

### Pane notes

```
$ zellij action set-pane-note build --color warn "waiting on review"
note: waiting on review
color: warn
```

A short line drawn on the pane's frame. The handle answers "which pane is this"; the note answers
"what is going on in it", which is the question a session full of agent-driven panes leaves a human
asking. Four colours named for what they mean — `error|warn|ok|info` — mapped onto whatever the
active theme picked for that meaning, so a note is legible in all of them.

**The server leaves one itself.** A command pane whose command exits non-zero and is held open is
marked `exit 7`, in `error`. The frame already said `EXIT CODE: 7` while the pane was held, but that
line goes when the pane is scrolled or re-run, and nothing outside the server could read it at all.
`list-panes` has a `NOTE` column and `list-tree` a `note:` field, both `error:exit 7` — colour and
words together, because a table without the colour cannot tell a pane that finished from one that
failed. A note is not saved into a snapshot: it describes live state, and a session restored
tomorrow should not come back carrying yesterday's "waiting on review".

### `list-tree`, `go-to-pane`, and text on stdin

`list-tree` is every tab with its panes nested beneath it — the join of `list-tabs` and `list-panes`
you otherwise had to do by tab id yourself:

```
$ zellij action list-tree
tab_id: 0  position: 0  name: develop  active: true
  handle: secure-wildcat  pane_id: terminal_0  title: zsh  command: /bin/zsh  focused: true
  handle: rapid-bass  pane_id: plugin_0  title: zellij:link  command: zellij:link  focused: false
```

`go-to-pane` is a visible alias for upstream's `focus-pane-id`, completing the `go-to-*` family. It
focuses the pane **and the tab it lives in**, and reports `from:` and `to:` as `<pane_id> <handle>`.
`--no-focus` turns it into the existence probe `go-to-tab-name` already had — which is what a handle
written down last week needs before anything is aimed at it — printing `id:` and `handle:` and
exiting 0 whether or not the pane is there.

`write-chars` and `paste` take their text from stdin when given no argument:

```
cat prompt.txt | zellij action write-chars --pane-id sunny-otter
zellij action paste --pane-id sunny-otter -    # `-` reads stdin even from a terminal
```

Text reaching a pane through an argument is escaped twice — once for the shell that types the
command, once for the shell in the pane — and a multi-line prompt does not survive that. A pipe
carries it as it is. No argument and a terminal is an error rather than an apparent hang; empty
stdin writes nothing and exits 2; the bound is 1 MiB, because the text is delivered as keystrokes
and the pane's program reads every byte.

### `subscribe --timestamps`

```
$ zellij subscribe --pane-id sunny-otter --timestamps
2026-08-14T18:03:12.345Z $ cargo test
2026-08-14T18:03:12.345Z test result: ok. 37 passed
```

A stream of pane renders with no times in it cannot answer "how long did that take", and a watcher
that stamps the lines itself has already lost the moment they arrived. RFC3339, UTC, to the
millisecond; a prefix in raw mode, a `ts` key in json. **It is a print time, not a server time** —
the clock is read by this client as the line leaves it, so there is no time here that could be
compared against another machine's. One stamp per update: every line of one render carries the same
time, because a stamp that crept forward between the lines of a frame would describe something that
did not happen.

### `list-events`: who moved your tab

```
$ zellij action list-events
AT                        VERB        TARGET                  ORIGIN    COUNT
2026-08-14T18:03:12.345Z  go-to-tab   tab_1 logs              client 1  1
2026-08-14T18:03:14.902Z  scroll-up   terminal_3 sunny-otter  client 1  38
2026-08-14T18:03:19.881Z  close-pane  terminal_3              cli       1
```

In a session a person and several agents are all driving at once, something changes and nobody knows
which of them did it — and every other query in this fork answers what the session *is*, not what
happened to it. The server keeps the last 256 things that changed, in memory, oldest first.

`ORIGIN` names the three ways an action arrives — `client 1` is somebody's keyboard, `cli` is a
`zellij action` call, `plugin 3` is a plugin — because all three pass through the one function that
routes an action. `TARGET` is the name that was true at the time. A run of the same verb on the same
target from the same origin is one row with a `COUNT`: a held scroll key is 38, not 38 rows, without
which the ring's whole capacity is one keypress.

Deliberately not in it: the `read` band, which by definition changed nothing; keystrokes typed into
a pane, which would be the whole ring (the same verbs *from the CLI* are recorded); actions that
failed; and the CLI's own plumbing. This is a ring, not a log — bounded, in memory, gone when the
server stops.

### `zellij session doctor`

```
zellij session doctor [NAME] [-n|--dry-run] [--fix|--no-fix] [--sign|--no-sign] [--exe PATH]
```

Everything that has to hold for one session to come up and stay up, checked in one pass. It repairs
what a program is allowed to repair and names what only a person can:

```
Changed
  pin       refreshed the pinned copy
            the running session keeps the old copy until it is restarted
Already correct
  path      this binary is the one a shell runs
  config    the config file parses
  socket    one server, this contract version
  agent     the launch agent is loaded
  domain    the server is in the graphical session, so its panes can reach TCC
Needs you
  fda       the server does NOT have Full Disk Access
            every pane sees "Operation not permitted" in a protected directory,
            whatever it runs. No program can grant this — Apple offers no API for it.
```

Exit 0 when `Needs you` is empty, 1 otherwise. That is the whole contract, so a script can call
doctor and read the answer without parsing it. **It never takes the session down**: a pin refresh, a
signature and a rewritten plist all take effect at the next start, so doctor makes the change and
*says* a restart is needed. For the same reason a drifted unit is reported rather than rewritten —
on launchd a rewrite means `bootout` then `bootstrap`, which stops the job.

Nothing is re-implemented: the unit and its drift come from the same calls `session status` makes,
the session from the same `SessionFacts`, the pin from the same `install_pinned_exe`. The two
commands cannot describe one machine differently.

**Everywhere**: which `zellij` a shell runs and whether it is this one; whether the config loads;
the socket directory, and any server serving this name from another one or under another contract
version; leftover wrapper scripts; the unit, its load state and its drift; one server and only one;
whether a dead session's saved layout is holding the name; whether the running server is this build;
the pin, and the temp copies an interrupted refresh left beside it. A leftover is narrow on purpose
— a script that merely calls zellij is a companion tool, and a `zellij` on the path that resolves to
this very binary is where zellij is installed. Two shapes are reported and never removed: a
different build taking the name, and a script that sets `ZELLIJ_SOCK_DIR` before zellij can resolve
it.

**Linux** adds what only systemd knows: whether the timer is armed — loaded and armed are different
states, and a disarmed timer beside a healthy install is how a session stops coming back — and how
the last run ended, read from `Result=` rather than `ActiveState=`, which cannot tell a failed run
from one that has not happened. Twenty journal lines are quoted under a failure and none under a
success. Signing and TCC report `n/a on Linux` rather than being left out: an absent line reads as
"checked and fine".

**macOS** adds `TMPDIR` against `getconf DARWIN_USER_TEMP_DIR`, the launch agent's label, and two
questions asked from inside a floating pane that closes itself: which session domain the server is
in, and whether it has Full Disk Access. Both are asked in a pane because neither is about doctor's
own process — macOS judges a terminal-launched process against the terminal's grants, while a pane
inherits the server's domain. Full Disk Access is asked by **opening** the user's `TCC.db` for one
byte: `[ -r ]` calls `access(2)`, which reads the permission bits, while TCC refuses at `open(2)`,
so a test on the bits answers "readable" on a machine holding no grant at all.

`--dry-run` withholds every fix, and the pane probe is the one thing it still does: it is a
question, not a repair, and the answer cannot be had any other way.

#### Signing the pinned copy (macOS)

macOS keys a grant for a non-bundled program to an absolute path plus a code requirement. An
unsigned or ad-hoc-signed binary has no identity to name, so the requirement is a hash of the
*code* — and the next build voids every grant, silently, until a pane fails in a directory that
worked yesterday. A signature anchored on a certificate ends that, and it runs by default;
`--no-sign` opts out.

Four rungs, first hit wins: **Developer ID Application**, which `codesign` already anchors on the
team id; **Apple Development**, whose requirement is written by hand and anchored on `subject.OU` —
never the CN, which carries an email that changes on reissue; **one we mint**, kept 0700/0600 with a
copy of `id.p12` in zellij's resolved config directory; and **nothing**, reported as the Xcode steps
under `Needs you`.

The minted certificate is the one file on the machine that cannot be replaced: **its own hash is the
requirement**, so a second certificate voids every grant recorded against the first. A keychain that
lost it is re-imported from the bundle rather than given a new one, and a backup copy that could not
be written is a `Needs you` naming the path the only copy is at — a user who believes a second copy
exists will never make one. It is never timestamped: Apple's server needs a real chain and would
only refuse. The first two rungs are, and where the attempt fails the signature is made without one
and the report quotes the refusal, because a signature that silently carries no timestamp looks
exactly like one that was never asked for.

Nothing is ever signed ad-hoc — that anchors on the code hash, which is the fault under a new name —
and no trusted root is ever added. The identifier is the constant `org.zellij.nkmk`; **changing it
voids every grant on every machine**, which is why it is a constant and not a setting. The round
trip is a copy, a sign, two verifications and a rename, because `codesign` writes in place and a
running server holds the pin open. The two verifications fail apart: a signature can verify while
its requirement still names the code hash, which is a run that reported success and fixed nothing.

**Doctor is also what sweeps the abandoned pin temps.** A refresh writes `.zellij.pin.<pid>.tmp` and
renames it; killed between the two it leaves 40 MB behind for good, because the next refresh writes
a new one under a new pid. Two gates: a temp whose pid is still running is never touched (`kill(pid,
0)`, with `EPERM` counting as alive), and a temp younger than an hour is left alone as a second belt
for a temp nothing has observed yet. It is doctor's job and not `install_pinned_exe`'s — that runs
before any lock, on every `session up` and every interactive launch, so two of them overlap
routinely and a sweep there would be one refresh deleting another's temp mid-copy.

### One warning badge in the tab bar

```
  mysession  1 edit  2 build  3 logs                              ⚠ zj TCC  7/30 3:47 PM
```

`zj` is a superseded build, `TCC` is missing Full Disk Access, and one triangle covers however many
are live — two triangles side by side read as two widgets rather than one thing that is wrong. **No
warnings renders nothing at all**, not a space, so a healthy session's bar is byte-identical to what
it was. It sits left of the clock rather than at the outer edge, so the clock keeps its column when
a warning appears or clears. Drawn in `exit_code_error` from the active theme, bold, and it never
blinks: it reports a fact that has been true for minutes.

**This replaced a pair of full-width lines the server composited over the top-right of the
viewport.** That placement bought real things, but the price was a sentence and a half of prose
across the top of the panes for a fact that does not change for hours. What is left of the old
design is the part that mattered: the **server** still answers both questions, because the answers
need `current_exe`, the `PATH` and a real `open` against a TCC-gated file, none of which a wasm
plugin can reach without spawning a process.

The answers ride **`ModeInfo.session_warnings`** — the one thing every bar already reads, already
reaching every tab's plugins. No new event type, no new subscription. An unknown code arriving over
protobuf is dropped rather than fatal, so a bar built against an older contract badges what it
understands. The trade is stated plainly: a user who has replaced **both** bundled bars sees neither
code, and `session doctor` is the tool for when something is actually wrong.

Full Disk Access is opt-in (`expect_full_disk_access true`, macOS), because only the user knows
whether they mean zellij to hold that permission. A superseded build (`stale_build_notice`, on by
default) is asked of the path this server was **started from** — the file being gone, or holding a
different build, is proof; comparing against whatever `zellij` is on `PATH` would call a
deliberately-mixed setup stale forever.

### Which panes are running a coding agent (`list-agents`, and an `AGENT` column)

```
$ zellij action list-agents
TAB_ID  TAB_NAME  PANE_ID  HANDLE       KIND    AGENT_ID  SOURCE       TITLE   COMMAND  CWD
1       develop   3        sunny-otter  claude  9f3c1a2b  command+env  claude  claude   /src
2       review    7        brisk-heron  codex   -         command      codex   codex    /src
```

"Send that to the develop agent" needs a way to turn a harness into a pane, and until now a caller
had to read `list-panes`, guess which commands were agents, and read the process table itself for
the identity.

**Detection is two-phase, and the split is why it is on by default.** Phase one costs nothing: a
pane's command is recorded already, and matching its basename against the harness table is a string
compare. Phase two runs only for a pane phase one matched, walking the pane's process subtree for
the harness's own session id — so **a session with no agent pane does not read the process table at
all**. And it runs once per pane, not once per second: a pane is walked when it appears, when its
process is replaced, and, only while nothing has been found, once every thirty seconds. Measured on
a session with one agent pane, the pty thread went from 9,800 read syscalls and 2.1 MB a second to
the same numbers as the same session with detection off.

`SOURCE` says which phase answered, so a reader knows whether a missing `AGENT_ID` means "the
harness does not export one" or "we never looked". `COMMAND` names the command line the row was
decided on — the pane's live argv when that is what matched, the line the pane was started with when
the fallback answered; the column exists to make a wrong row obvious, and cannot do that while
showing a line the row was not decided on.

It is on the cheap surface deliberately: `agent` is a field on `PaneListEntry`, which is CLI-only,
and **not** on `PaneInfo` — no protobuf tag, nothing to carry through a rebase. `list-agents` adds
no `Action` either; it is answered by the client from one `list-panes --json`. `detect_agents false`
turns off both phases, and being top-level it is ignored by a binary that predates it.

### `zellij mcp`: the CLI served over the Model Context Protocol

```json
{ "mcpServers": { "zellij": { "command": "zellij", "args": ["mcp"] } } }
```

`setup --dump-surface` already describes the whole tree, which is most of what an agent needs. What
it cannot do is help a harness that **cannot shell out**, and it cannot be gated per verb — an MCP
client allows or denies each tool by name, which on a machine where "read a pane" and "close a tab"
want different answers is the whole point.

**Seven tools, not eighty-seven**: `zellij_overview`, `zellij_read_pane`, `zellij_wait_for`,
`zellij_write_input`, `zellij_create`, `zellij_arrange`, `zellij_snapshot`. Session lifecycle is
deliberately not among them — those start and stop the thing the server is talking to. A test fails
if the surface grows past eight tools, or a tool past eight parameters.

**The descriptions are generated from the surface map.** A tool's `Returns:` line is built from the
same row `--dump-surface` prints, and each input-schema property standing for a real flag carries
clap's own help. Rename a flag in `cli.rs` and the build fails rather than the description going
stale. Only the routing prose — what a tool is for, and which tool to reach for next — is written by
hand.

**Every tool runs this same binary as a child process** rather than calling the action path
in-process: that path prints to stdout and exits on a miss, and on a stdio server stdout is the
protocol stream and the process is the session. A child also maps the fork's exit convention
straight through, which is what lets `zellij_create` be honest — a pane that was not made reports
the CLI's own refusal, and there is no id anywhere for it to invent. Every child is spawned with
`kill_on_drop`, so an abandoned call takes its child with it.

New dependency: `rmcp` (the official Rust MCP SDK) with `server` and `transport-io` only — eight
crates, no HTTP stack, and nothing on any wasm plugin crate.

## Fixed

### A pane is reported only once a tab has taken it

Upstream reports a new pane **as soon as its pty spawns**, which is before any tab has agreed to
hold it. A tab that declines does so by dropping the pty rather than by failing, so the CLI printed
`pane_id:` and `handle:` and exited 0 for a pane that was never made:

```
$ zellij action new-pane --in-tab 1 --handle ghost1
pane_id: terminal_1
handle: ghost1                        # exit 0, and terminal_1 is in no `list-panes`
```

The id is now written into the report **after** the placement, and only for a pane some tab really
holds. A miss says so and exits 2: `No pane was created: the session took the request and reported
no pane.` It is one rule in two halves — the session stops asserting an id it only asked for, and
the client holds each pane-making verb to answering with a pane. Any future route that declines a
pane is reported honestly without knowing about this.

#### The miss has to be a real one

Holding the client to a report makes a lost report indistinguishable from a pane that was never
made, and that is what `new-pane --handle` did about one call in ten: the pane was there in
`list-panes` under a generated handle while the CLI said none had been made.

Nothing about the pane was at fault. `--handle` is checked against the live panes before anything is
created, and that check is a whole extra connection, closed immediately before the one carrying the
`new-pane`. A client id is the lowest number not in use, so in a session nothing is attached to both
connections are client 1 — and a route thread announced its client's removal twice, once as the
client left and once as the thread ended. The first announcement freed the id, the next connection
was given it, and the second announcement removed **that** connection's sender. Dropping a sender
writes an `Exit { Disconnect }` down its socket, which the waiting client read as the answer to its
`new-pane`.

A route thread now announces its client's removal exactly once, after its last act, and the id
cannot be handed out while that thread can still reach it. The client also stops reading a
disconnect as an empty report: it is a dropped connection, said out loud, and exits 1. `--in-tab`,
`--near`, `zellij run`, `zellij edit` and `--plugin` all travel the same path and are all covered.

### A session nothing answers to is a miss, not a listing on stdout

```
$ zellij -s no-such-session action list-panes --json
                                      # nothing on stdout
Session 'no-such-session' not found. The following sessions are active:   # stderr
work
notes                                 # exit 2
```

It used to exit 0 with the `ls` table on stdout, so a script that mistyped a session name got a
successful answer of the wrong shape. Every such path printed its sentence and then called
`list_sessions`, which writes the table to stdout and ends in `process::exit(0)` — making the
`exit(1)` written on the next line unreachable. The same held for `zellij attach` with no session to
choose from. Only the listing that was **asked** for, `zellij ls`, still goes to stdout.

### Making a tab needs somebody attached

A tab is built by applying a layout, and applying one needs a client to size it against. On a
session nobody is attached to, the whole tab-creating family — `new-tab`, `new-tab --layout`,
`new-pane --new-tab`, `go-to-tab-name --create` — used to make an **empty** tab, report a `pane_id:`
for a pane that never existed, and have the tab thrown away by the next client to attach. A script
got a success and an id, and nothing was there.

They now refuse with exit 2 and create nothing. This is a refusal rather than a fix: a detached
session applying its own layouts is the real answer and is a separate piece of work. The session's
own startup is untouched — it builds its tabs before any client attaches, and that is exactly what
tells the two cases apart: a command has a caller waiting for an answer, and startup has none.

### Four verbs report a target nothing answers to

`rename-tab --tab-id`, `edit-scrollback --pane-id` and `toggle-pane-borderless --pane-id` logged a
miss server-side and exited 0, which reads as a rename, an editor and a toggle that happened. Every
sibling that takes the same target already exited 2 with a sentence, so this was a gap in the
exit-code sweep rather than a choice. `go-to-tab` is the same shape in one state only: with nobody
attached there is no client to move, so the switch was queued for a tab that was never coming.

`are-floating-panes-visible` was worse than a gap: it printed a bare `true` on stdout and sent
`false` as an **error** message, which the CLI turns into exit 2 — so the answer `false` left with
the exit code of a miss and no way to tell the two apart. Both answers now leave as one stdout line,
`visible: true` or `visible: false`, exit 0 either way. A tab nothing answers to stays a real miss,
which is what makes the stdout answer mean something.

`close-pane` with nothing focused on a detached session is a miss too, rather than a silence.

### A layout's pane count is the panes it produces

`is_dirty` decides whether a serialization tick has anything to write, by comparing the panes the
session has against the panes its layout describes. `Layout::pane_count` answered that second
question wrong: a layout carries tabs **and** a template, and the parser fills the template in even
for a layout that declares its own tabs. Counting both added the template's panes on top of the tabs
they had already built, so a real layout file reported more panes than any session it could produce
— one layout in daily use claimed 40 panes for the 36-pane session it built — and every session
grown from one was dirty from the moment it started.

The count now branches the way the spawn loop branches: tabs if the layout has tabs, the template if
it has none. Two things follow. A clean session stops rewriting the cache, which was the point; and
the rest of `is_dirty` becomes reachable at all, since the count returned first every time. A
session that returns to its base shape still rewrites it once more — opening a pane and closing it
again would otherwise leave the file on disk diverged with nothing to overwrite it.

### What a clean session still has to write

Being able to be clean brought a new way to be wrong. `is_dirty` asks whether the session diverged
from the layout that built it; the cache holds a copy of the **session**. Rename a pane and the pane
count, the tabs and the commands are all the same — so the session is dirty by nothing, writes
nothing, and the copy on disk keeps the old name for as long as it stays clean. Every serialized
attribute the dirty checks do not look at has that shape: cwd, geometry, pinning, borderlessness,
focus, uuid, handle, colours, viewport contents.

A tick now also writes when the layout it *would* write differs from the one it last wrote, decided
by a fingerprint over every field reaching `GlobalLayoutManifest`, taken from metadata the tick
already gathered — nothing is serialized to compute it. Both metadata structs are destructured field
by field, so a field added later fails to compile until someone says which side of the fingerprint
it belongs on. The geometry is hashed through its `Debug` rendering, because `PaneGeom` hashes
without `is_pinned` on purpose and the serialized layout writes `pinned`. A clean, unchanging
session is still silent.

### A moved tab makes the layout dirty

`is_dirty` asked about the pane count and the commands panes run. Moving a tab changes neither, so a
session otherwise in the shape of its layout never wrote its layout again after a move — and a plain
`up`, which resurrects from `session-layout.kdl`, brought the tab back where it started, on every
restart. The check now also compares the tab list against the base layout's tabs: count, name and
**order**. A base layout with no tabs of its own is not compared, and an unnamed base tab matches
any name.

### `session restart` holds one lock across both halves

A restart racing the watchdog's minute tick lost its `--restore`, and the case it exists for is the
worst one: restoring a shape after a reboot, which is exactly when a watchdog is ticking. `restart`
is a `down` and then an `up`, and the lock was taken **inside** `up` — so the window between the two
steps was unlocked, the tick's `up` took the lock first and built the session fresh from the layout,
and the restart's `up` then found a healthy session and discarded the snapshot it had just archived.

`restart` now takes the lock once, before `down`, and holds it over both steps. `lock_up` is
re-entrant within one thread, because `flock` is per open file description and a second descriptor
would block against itself for the full timeout. Two threads racing for one name still contend at
the `flock`, as two processes do.

The timeouts had to move with it. `session up` gave a freshly requested server 10 seconds to appear
where launchd was measured at 15 to 20, so both reported a post-condition failure on sessions that
were up moments later — and a false failure on a healthy machine is worse than a slow true one,
because it is the shape a real fault takes. The server wait is now 30 seconds and the up-lock 90, so
a `down` plus an `up` still fits inside the lock with margin; a test asserts the ordering, and now
parses `--wait-timeout`'s default out of clap rather than copying the number in as a literal.

### Pin hardening

Six fixes on the pinned copy of the binary, which is what keeps macOS grants attached to a path an
upgrade does not move.

- **The refreshed copy is renamed into place, not written through.** `install_pinned_exe` opened the
  pinned path with `truncate`, on the belief that TCC keys a grant to the inode. `TCC.db` has no
  inode column — a non-bundled client is keyed by absolute path plus a code requirement — and an
  in-place overwrite loses the grant anyway. It cost something real: the kernel kept the old cdhash
  for the vnode, so a session refreshed while it was up died on the next launch with
  `OS_REASON_CODESIGNING` while `codesign --verify` called the file valid.
- **The copy reaches the disk before the rename puts it in use.** `rename(2)` is atomic against
  another process and orders nothing against the disk, so a machine that lost power mid-refresh came
  back with a short file at the pinned path — and nothing above could see it, because the stamp
  beside the pin describes the *source*, and the source was intact. The temp is now fsynced before
  the rename and the directory after it.
- **The pin is judged by the source it was made from.** Comparing the pin against the binary beside
  it stops being the right question as soon as the pin is signed, because signing changes the copy
  on purpose — so a signed pin read stale forever and a watchdog's `session up` copied over the
  signature within the minute. The SHA-256 of the source is recorded in `<pin>.source-sha256`.
- **A source that is its own target is refused before it is copied.** Once the launcher execs the
  pin, `session up` hands the pin to `install_pinned_exe` as its own source. On macOS that
  self-compare found a stamp not matching the signed pin's bytes, called it stale, copied it over
  itself and **re-stamped it with the signed copy's hash** — after which the next run off `PATH`
  called the pin stale again and copied the unsigned package over the signature, taking every grant
  with it. Asked of the inode, not the spelling.
- **The hash cache is keyed on the stat taken before the hash.** Deciding the pin is current meant
  hashing 40 MB on every `session up` — around 75 ms, every minute from the watchdog — so
  `<pin>.source-key` records the hash beside what the source looked like to stat. The key was
  recorded from a re-stat taken *after* the copy against a hash computed before it, so a source that
  changed under the run cached "new identity ⇒ old hash" for as long as it then sat still. It is a
  cache and not an answer: the stamp still decides staleness, and anything the key is unsure about
  falls through to hashing.
- **The signing sweep no longer takes the temp of a run still signing.** It removed every
  `.zellij.sign.*.tmp` with no gate at all — and the temp of a signing run happening right now is
  named exactly that way, so two overlapping runs meant `codesign` writing into a deleted inode.
  Both prefixes now ask the same two questions from one implementation, with separate call sites so
  neither sweep can reach the other's files.

### A plugin whose file is missing stops erroring on every layout dump

A plugin that fails to load leaves its pane behind but nothing in `plugin_map`, so its id resolves
to nothing and `populate_session_layout_metadata` logged `Plugin with id: N not found` on every
serialization tick for the life of the session. The pane meanwhile serialized with no plugin at all,
so the next snapshot recorded a plain pane where a plugin used to be. A snapshot taken before this
fork swapped its bars for builtins restores exactly this — `file:` panes pointing at `.wasm` files
that no longer exist — and nothing can migrate those recordings, so the failure has to degrade
quietly.

The `RunPlugin` of a plugin that failed to load is now kept for as long as its pane lives. Dropping
the pane instead was the alternative, and was rejected: a restore that silently deletes panes is
worse than one that shows which plugin is gone, and keeping the plugin in the serialized layout
means restoring works again the moment the file comes back.

### Resume hints are built from the argv the pane really ran

A restored pane offered `claude --resume <uuid>` and running it answered that no session by that
uuid exists. Neither half of that command line was ever run: the live process was `claude
--dangerously-skip-permissions --continue`. `resurrect_command_hints` **replaced** the observed
command line with a template — every flag the pane actually ran was dropped, the interpreter path
with them, and the environment value was pushed into the command whether or not it belonged there.

A hint now only **appends**. `resume_args` replaces `rewrite` and holds arguments, not a command
line, so the pane's own command and arguments are kept whole. A hint adds nothing when any of its
words is already in the observed arguments: a pane started as `claude --continue` already says how
it resumes, and its argv beats a reconstruction.

**Migration:** every config that says `rewrite` must be edited, and the value changes shape as well
as key — `rewrite "claude --resume {}"` carries the command name and `resume_args` must not:

```kdl
resume_args "--continue"        // was: rewrite "claude --resume {}"
resume_args "--session {}"      // was: rewrite "opencode --session {}"
```

Until that edit lands, `rewrite` is warned about and its hint skipped, and the rest of the config
loads. It is not refused: `Config::from_kdl` fails the whole file, so refusing the key would stop a
machine over a stale hint. A skipped hint costs a resumable command; a refused config costs the
session.

### A live warning is re-sent on every tick

A session started **on** a superseded build showed nothing, for as long as it ran. The first tick
fires as the server starts — `tokio::time::interval` completes immediately — which is before any tab
exists and before a bar has loaded, so the broadcast reached nobody; and because the answer never
changed after that, the next tick took the early return. Only a warning that appeared *after* a bar
was up was ever seen. A non-empty set is now re-sent every tick; the bars drop an update matching
what they already hold, and clearing still needs a change.

## Changed

### The session manager's Enter key

Enter on the row you are already attached to had one answer — "Already attached to this session." —
which is a sentence the person pressing it already knew. The row is selectable, every other key acts
on it, and the one key everybody presses first spent itself on a notice. It now opens the
connected-clients list, the same screen `Ctrl+l` opens and by the same call, so the two entrances
cannot drift apart. Enter on any other session still attaches, and the prompt's hint follows: the
current session's row reads `<ENTER> - Clients` where the others read `Attach`.

## Upstream

`git fetch upstream` reports no commits past `f42ca3c79`. The base is unchanged since nkmk.1.

**The plugin API changed**: `PaneInfo` gains `handle` (proto tag 46), and `ModeUpdatePayload` gains
`session_warnings` (tag 23) with a new `SessionWarning` enum. Both are new tags on existing
messages, so a plugin built against nkmk.5 keeps working — it decodes them as unknown and ignores
them. An unknown warning code is dropped rather than fatal, which is what lets an older bar badge
what it understands. Rebuild against this release's `zellij-tile` to read the new fields; the
bundled plugins, including the two builtin bars, are rebuilt here.

**The client/server contract changed, additively.** Five new message tags — `resolve_pane_target`
(167), `list_tree` (168), `set_pane_handle` (169), `set_pane_note` (170), `list_events` (171) —
plus `pane_handle` on both layout messages and a `no_focus` field on `FocusPaneByPaneIdAction`. The
tag `query-tab-names` used to occupy stays assigned and its message stays defined, because a client
of an older build still sends it and the wire contract is append-only. Nothing existing was
renumbered, so a fork client and a stock server of the same contract still share sessions.

## For consumers

What a script written against nkmk.5 has to change:

- **Parse `pane_id:` lines, not a bare id.** `new-pane`, `new-tab` and `edit` print `pane_id:`,
  `handle:` and `tab_id:` where each applies. A creation that printed nothing means no pane was
  made, and exits 2.
- **`close-pane`, `close-tab`, `kill-session` and `delete-session` need `--yes` off a TTY.** Without
  it they refuse and exit 2 rather than prompting into a pipe. `clear`, `snapshot rm` and `snapshot
  prune` are in the same layer.
- **Exit 2 is a wider bucket than it was** — a miss, a refusal, a declined or unanswerable confirm,
  a `wait` that timed out, and a usage error clap would not accept. It is never a failure. **Read
  stderr**, which is what says which door the call came through; the exit code alone no longer
  narrows it.
- **`new-tab` and every other tab-creating verb refuse on a session nobody is attached to**, exit 2,
  where they used to report a `pane_id:` for a pane that was thrown away.
- **`move-tab` without `--tab-id` acts on the focused tab**, and each transient CLI client resets
  focus to the first tab — so from a script that is tab 1, not the tab you meant. The same holds for
  every class-2 verb: name the target. Class-3 verbs (`close-pane`, `write`, `write-chars`,
  `send-keys`, `paste`) now refuse outright without one.
- **`query-tab-names` is gone.** Use `list-tabs`.
- **`are-floating-panes-visible` exits 0 for both answers now**, printing `visible: true` or
  `visible: false`. A script testing `$?` for the answer must read stdout instead.
- **`resurrect_command_hints` `rewrite` is deprecated** in favour of `resume_args`; see the
  migration above.
