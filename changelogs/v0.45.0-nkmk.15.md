# v0.45.0-nkmk.15

- **Upstream base:** `98a083707` on upstream `main` (workspace version `0.45.0`) — unchanged since
  nkmk.13
- **Range:** `v0.45.0-nkmk.14..main` (1 commit)
- **Released:** 2026-08-18

Three macOS lifecycle fixes with one theme: the pinned, signed binary is only worth anything if it
is what launchd runs and what doctor can sign. Before this release, neither held on a real machine.

## Fixed

### `session up` and `session restart` create the session through the launch agent

`gui_domain_action` returned `Proceed` whenever the caller was already in the graphical (`Aqua`)
domain, so `zellij session restart` typed in a pane never asked launchd for the job. The new server
was a child of the client at the Homebrew Cellar path. macOS attributes the server's
Desktop/Documents/Downloads probe to that responsible process, and the Cellar path changes on
every upgrade — hence a TCC prompt after every `brew upgrade` even though the pin was signed and
granted.

Now, when the session is absent and a loaded launch agent exists for it, `up` kickstarts the
agent even from inside `Aqua`. The job's own `session up` recognises itself through launchd's
`XPC_SERVICE_NAME` (with a `launchctl print` pid check as fallback) and does not recurse. No plist
change: every installed agent already carries that variable, so no `session enable` re-run is
needed.

The up-lock is handed over before waiting on the kickstarted job. Without that, the job's `up`
blocked on the flock the caller held and every deferred `up`/`restart` reported
`post-condition FAILED` after 30 s while the session came up anyway.

Escape hatch, in case a machine needs the old path back without a release:

```kdl
session_service {
    restart_via_launchd false
}
```

Nested key: an older binary rejects the whole config on it, so add it only after upgrading.

### Doctor sets aside a signing bundle that is not its own

`ensure_self_signed` re-imported an existing `signing/id.p12` and, if the keychain still offered no
`zellij self-signed code signing` identity, fell through to "no signing certificate for <pin>" —
forever, because the bundle existed so it never minted. An earlier `zellij-mac-setup` wrote exactly
such a bundle under a different name. Knock-on: `refresh_pin_through_signing` failed, so the pin
stayed on the previous build after an upgrade.

Doctor now re-asks the keychain after the import; if the ladder still has no self-signed rung, it
moves the bundle to `id.p12.foreign-<ts>`, says why (naming the foreign certificate when it can),
mints its own, and signs. TCC grants for the pin must be re-made once on such a machine.

### The pin is not stale against itself

`pin_needs_refresh` lacked the same-file guard `install_pinned_exe` has. Doctor run *as* the pin
saw the pin as stale, copied it over itself, re-signed, and re-stamped with its own hash; the next
run from the package path copied back over the signature. The two alternated on every run.

## Upgrade notes

- Macs: `brew upgrade zellij-nkmk`, then `zellij-mac-setup` (it now delegates signing to
  `zellij session doctor --fix --sign` and sets aside the legacy bundle), then `zjr`. Expect one
  TCC re-prompt on machines that carried the legacy `zellij-nkmk local signing` certificate.
- Linux: no behaviour change.
