# v0.45.0-nkmk.14

- **Upstream base:** `98a083707` on upstream `main` (workspace version `0.45.0`) — unchanged since
  nkmk.13
- **Range:** `v0.45.0-nkmk.13..main` (1 commit)
- **Released:** 2026-08-17

One fix, one line of code, and a symptom that pointed nowhere near it. Over mosh, the right-most
column of the screen was losing characters — a ragged vertical gap down the edge of every pane,
worse the more colour a program used. It read as a mosh bug, or a font bug, or a width bug. It was
zellij's OSC 8 hyperlink terminator.

## Fixed

### OSC 8 hyperlinks end with BEL, not ST

`TERMINATOR` in `zellij-server/src/panes/link_handler.rs` is now BEL (`\x07`) instead of the 7-bit
string terminator (`ESC \`). Both the link start and the link end read that one constant, so both
change together.

The reason is mosh. `mosh-server` up to and including 1.4.0 does not parse OSC at all. Its terminal
emulator hands the whole sequence to an unknown-escape path, and that path clears the pending-wrap
flag as a side effect (mobile-shell/mosh#687). Pending-wrap is what remembers that the cursor has
written the last column and must wrap before the next character; clearing it discards the cell that
was waiting there.

Zellij emits an OSC 8 link *end* after every style reset, which in practice is at or near the start
of essentially every rendered row. So over mosh the flag was being cleared constantly, and a styled
run that reached the last column lost its final cell each time. BEL takes a different path in that
emulator and leaves the flag alone.

Nothing is given up. BEL is the older of the two OSC terminators and every terminal this fork
targets accepts it — zellij already ends its own window-title OSC with BEL. Links stay clickable in
Ghostty, iTerm2 and kitty, and `osc8_hyperlinks true`, which is the default, stays usable over mosh
instead of having to be turned off to get a clean right edge.

The two unit tests in `link_handler.rs` build their expected strings from `TERMINATOR`, so they
follow the constant rather than pinning the old bytes. Proved end to end as well: a pty client
attached to a scratch session captured 174 OSC 8 sequences, all BEL-terminated and none
ST-terminated.

Deliberately unchanged: `zellij-utils/src/setup.rs` still writes ST-terminated links. That is the
`zellij setup --check` report, printed by the CLI to its own stdout rather than drawn through a
pane, so it is not on the path that loses the cell.
