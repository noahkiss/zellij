# v0.45.0-nkmk.7

- **Upstream base:** `f42ca3c79` on upstream `main` (workspace version `0.45.0`) — unchanged since
  nkmk.1
- **Range:** `1f6870c4c..main` (3 commits)
- **Released:** 2026-08-15

One fix. `zellij session doctor --fix` could not sign on either of the two Apple rungs, and gave up
on the first refusal instead of trying the other — so a Mac holding a real certificate was left with
the ad-hoc-signed pin that signing exists to replace. Both refusals are fixed and the ladder is now
walked.

## Fixed

### A signing rung that refuses is walked past, not stopped on

Two failures, found on a real Mac running nkmk.6, on the two rungs the release binary had never
been driven through.

The **Apple Development** rung wrote a bare requirement expression. `codesign -r` parses what it is
handed as a requirement *set*, so a text opening with `identifier` puts a reserved word where a tag
belongs, and the rung was refused before signing began:

```
Requirement syntax error(s): line 1:1: unexpected token: identifier
```

The text now opens with `designated =>`. The `-r=<text>` argv was never at fault — the leading `=`
already selects inline text over a file — and it now says so in a comment, so the next reader does
not go looking there.

The **minted** rung wrote a PKCS#12 with OpenSSL 3's defaults, which Apple's importer refuses and
reports as a password nobody gave it:

```
SecKeychainItemImport: MAC verification failed (wrong password?)
```

The bundle is now written with a SHA-1 MAC and PBE-SHA1-3DES. `-legacy` is tried first and dropped
on failure: macOS ships LibreSSL as `/usr/bin/openssl` and LibreSSL has no such flag, while a
Homebrew OpenSSL 3 may be first on `PATH` instead.

Either failure used to end the run on a `Needs you`, which is the worse of two outcomes — `session
up` refreshes the pin ad-hoc-signed and doctor is what makes it anchored, so giving up left the
machine in the exact state signing exists to remove, with a working certificate standing one rung
below. The two Apple rungs are now **walked**: a refusal tries the other, and the signature that
lands names the rung above it that would not sign. Only a copy or a rename the filesystem refused
stops the walk, because another certificate would write the same error twice.

The walk stops at the Apple rungs, and that boundary is the point. Developer ID and Apple
Development of the same team carry the same designated requirement, so falling between them keeps
every TCC grant; the certificate we mint is anchored on its own hash and does not. A refusal is also
not always the certificate's fault — `errSecInternalComponent`, a keychain locked over SSH, a denied
key-access dialog — and demoting the pin on one of those would be permanent, because a self-signed
signature *is* anchored and the next run reads the pin as already correct. So the rung we mint is
reached only when the keychain offers no Apple certificate at all, and a machine that holds one and
cannot use it gets a `Needs you` naming what each certificate said.

**Known limitation, recorded rather than guarded:** the same-team reasoning above is not enforced.
The walk compares neither team id nor the requirement it would derive, so a keychain holding
certificates from two *different* teams would fall to a different `certificate leaf[subject.OU]` and
drop every grant. One machine holding both, from two teams, is rare.

## Changed

### The tap bump is dispatched by the release workflow

`release.yml` gains a `bump-tap` job that runs after `finalize` — once the release is published with
every platform's assets attached. It dispatches `bump-zellij.yml` in `noahkiss/homebrew-tap` and
waits for that run, so the formulae are rewritten from the release's own `.sha256` assets and proved
with a real `brew install` before anything is committed. No sha is transcribed by hand, and no
formula is hand-edited.

The dispatch needs `HOMEBREW_TAP_TOKEN`, a PAT with `workflow` scope on the tap, because this
repository's `GITHUB_TOKEN` cannot dispatch another repository. Without it the job prints the
manual fallback and passes, so a release never fails for want of the token.
