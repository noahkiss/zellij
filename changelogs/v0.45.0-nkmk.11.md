# v0.45.0-nkmk.11

- **Upstream base:** `f42ca3c79` on upstream `main` (workspace version `0.45.0`) — unchanged since
  nkmk.1
- **Range:** `v0.45.0-nkmk.10..main` (1 commit)
- **Released:** 2026-08-15

Three releases have now gone at the same feature from the same proof — signing the pinned binary on
a Mac that holds no Apple certificate. nkmk.9 stopped doctor hanging on a terminal password prompt.
nkmk.10 granted the key ACL on every run, not only on the run that minted the certificate, and made
the report quote the refusal instead of the line above it. Both of those made signing *work*.

**nkmk.11 fixes the order the work happens in.** It was found on the machine that proved nkmk.9: a
run where signing is refused had already replaced the pin. Upgrade to it from any of nkmk.8, .9 or
.10.

## Fixed

### The refresh outran the signature

Doctor copied the new build over the pin **first** and signed it **second**. So a run where every
signing rung refused — a locked keychain, which is **every** unattended launchd run — had already
overwritten a properly anchored pin with a fresh ad-hoc copy. It then reported that the pinned copy
was untouched. That sentence was true only of the signing step's temp file. The pin was gone, and
every permission grant on the machine was void from the next restart — a symptom that surfaces
later, somewhere else, and reads as a different bug.

The two steps are now one transaction. When the pin is anchored and out of date, the new build is
handed to the signing step, which writes it into its own temp, signs that, verifies it, and renames
only on success. A refusal leaves the previous signed pin exactly where it was — previous build,
signature intact, grants intact — and the report says **"NOT refreshed"** instead of claiming
nothing was touched.

One function decides the deferral and both steps ask it. A disagreement in the "skip" direction
would drop the refresh with nothing reporting it. It lives in `zellij-utils` so it compiles and is
tested off macOS.

A pin that is **already** ad-hoc is still refreshed first, as before. It holds no grant a rebuild
could keep, so pinning the new build is worth more than protecting a signature that was never
load-bearing.

### The re-grant note fired when nothing had changed

Whether to send the user back into System Settings was inferred from the **state of the machine**: a
bundle in the signing directory meant "this machine signs with a certificate of its own". A Mac
carrying leftovers from an older shell script was therefore told to redo three permissions against a
requirement that was character-for-character the one already recorded.

It is now decided by comparing the requirement **text** read off the pin before signing with the
text read off the signed copy after. Same text, no re-grant, and the advice drops to the one step
that is actually needed: the restart. That is the ordinary case — a pin re-signed with the same
certificate carries the same requirement, which is the whole premise of the feature.

### Three smaller ones from review

- The stamp recorder is `#[cfg(unix)]` and the signing flow that calls it compiles on Windows too.
  It gets a `not(unix)` stub rather than a `cfg` at the call site.
- The signing rename now fsyncs the temp before it and syncs the directory after — what
  `install_pinned_exe` has always done, and what this rename earns the moment it *becomes* the pin
  refresh.
- The fatal branch — a copy or a rename the filesystem refused — now reports what became of the pin
  through the same helper the exhausted ladder uses, instead of asserting the pinned copy is
  untouched when a deferred refresh means something more useful is true.

## Recorded, not fixed

Two findings from the same proof are written into `FORK.md` beside the code they qualify:

- **`codesign --verify` exiting 0 says nothing about whether a grant survived.** It answers "is this
  signature intact", not "is this the requirement macOS recorded".
- **The `build` check compares the pin FILE to the running build**, so it goes green while the old
  server process is still the one running. Pre-existing, unchanged here.

And the remaining gap: **`session up` still refreshes the pin on its own, with no signing step.** An
upgrade whose first command is `session up` puts an ad-hoc pin in place exactly as the old doctor
did. The fix belongs with `session up` and is not a signing change.

## Upstream

The base is unchanged at `f42ca3c79`; `git fetch upstream` reports 6 commits past it, none taken. No
plugin API change and no contract change: a plugin built against nkmk.6 or later keeps working, and
the bundled plugins are unchanged.
