# v0.45.0-nkmk.18

- **Upstream base:** the `v0.45.0` release tag (`13e1c25a2`) — unchanged since nkmk.17
- **Range:** `v0.45.0-nkmk.17..main` (43 commits)
- **Released:** 2026-08-27

The release where the fork stops making a program guess. A consumer polling `list-panes` can now
read which tab a pane is in, which clients are looking at it, and whether its command is still
running; six structural events say when a tab, a focus or a client changed, instead of leaving that
to be recovered by diffing snapshots; `subscribe --all` takes the whole session including panes that
do not exist yet; `zellij action --json` answers the mutations; and `zellij pipe` answers at all.
Around that, three separate ways a session could be taken down or hung — a wedged server that hung
every listing machine-wide, a client whose terminal died, an `accept` that failed at the open-file
ceiling — and the screen corruption over SSH that one two-line default had been causing all along.

## Added

### `PaneInfo` says which tab its pane is in

`PaneManifest` is keyed by tab **position**, and a position moves whenever tabs are reordered. So a
plugin holding a manifest could not say which tab a pane was in: the key it had was not an identity.
`PaneInfo.tab_id` is the same stable id `TabInfo.tab_id` reports, so the join is one field lookup, it
survives a reorder, and it needs no second event.

`PaneListEntry` drops the `tab_id` of its own it used to carry — it flattens `PaneInfo` into the
same JSON object, so keeping both would write the key twice. The CLI output is unchanged. The field
crosses the plugin API: `event.proto` tag 47, both `TryFrom` implementations, and the KDL codec
behind `session-metadata.kdl`, read back optionally so older metadata still parses.

### `PaneInfo` names the clients looking at a pane

```
zellij action list-panes --all --json | jq '.[] | {id, is_focused, focused_by_client_ids}'
```

`is_focused` is one boolean for the whole session, so with a human and an agent attached — the
normal case here — a consumer could not tell who was looking at what. `focused_by_client_ids` lists
the connected clients focused on this pane, ascending. `is_focused` is unchanged and is the same
answer collapsed: true exactly when the list is not empty.

A focus move *inside* a tab now refreshes the manifest as well. It only rendered before, so
`is_focused` described the focus the session had before the move until something else happened to
report. `event.proto` tag 48; no client list is added to `SessionInfo`, which already says this
twice.

### Whether a pane's command is still running (`command_state`)

```
$ zellij action list-panes --all --json | jq '.[] | {handle, command_state, last_command_exit_code}'
{"handle":"sunny-otter","command_state":"running"}
{"handle":"brave-heron","command_state":"done","last_command_exit_code":1}
{"handle":"quiet-lark","command_state":"prompt"}
```

A shell that emits OSC 133 says exactly where its prompt starts and where a command ended, with its
exit code. zellij has parsed those markers for a while and used them for one thing — the triple-click
that selects a command and its output. Nothing could read them, and they are the only exact answer
to "is this pane busy"; everything else in the tree infers it.

Both keys are **absent** for a shell that emits no markers and for a plugin pane, which is a
different thing from `prompt`. `PaneListEntry` is CLI-only, so this costs no protobuf tag and
nothing plugin-visible.

### Six structural lifecycle events

`PaneClosed`, `PaneOpened` and `PaneExited` were the only structural events in the tree. Everything
else — a tab appearing, being renamed or closing, focus moving, a client arriving or leaving — had
to be recovered by diffing successive `TabUpdate` and `PaneUpdate` snapshots, which is work every
consumer repeats.

| Event | Payload | Fires when |
|---|---|---|
| `TabAdded` | tab id, position, name | a tab is created, from any path including a layout |
| `TabRemoved` | tab id | a tab closes |
| `TabRenamed` | tab id, new name | a tab's name changes, from any source |
| `FocusChanged` | client id, pane id, tab id | a client's focus moves, to another pane or another tab |
| `ClientAttached` | client id | a client attaches |
| `ClientDetached` | client id | a client detaches, or its connection goes away |

All six are broadcast like `PaneClosed`, so they reach background plugins and plugins in tabs nobody
is looking at, attached or not. Focus is per client and says nothing about the others. Four of the
six are found by diffing at `log_and_report_session_state`, so a path added later cannot forget to
announce itself; focus is diffed from `render_to_clients` as well, because moving focus inside a tab
never reaches the report. `event.proto` gains `EventType` values 55–60 and payload tags 49–54.

### A title a program sets for itself reaches plugins

A pane title set with OSC 0/2 updated zellij's own state but produced no `PaneUpdate`, so a plugin's
cached titles went stale for exactly the panes whose program renames them — which is most of them.
`list-panes --json` was right immediately; a subscriber heard nothing until some unrelated event
rebuilt the manifest. Upstream [#5482](https://github.com/zellij-org/zellij/issues/5482).

The OSC title is the one pane state change that arrives as pty output rather than as an instruction,
so it never touched the reporting path. It now reports a change of **value**, not a write — most
shells rewrite the same title on every prompt. Only the pane manifest is rebuilt. No plugin API
field is added; `program_title` already ships.

### `subscribe --all`: every pane, including the ones that do not exist yet

```
zellij subscribe --all --format json
```

A subscription had to name its panes, so a consumer that wanted the session had to run `list-panes`
first and re-subscribe on every new pane — and saw nothing of that pane in between. `--all` asks for
the session instead. A pane opened later joins the feed on its own, arriving as an initial delivery
so a consumer can tell a pane it has never seen from one that merely changed.

`--all` and `--pane-id` are mutually exclusive and one is still required. A wildcard outlives its
panes and runs until the session does. `pane_privacy` is honoured, re-filtered on every delivery
rather than once at subscribe time, which is why the expansion had to live in the server. The flag
rides the existing `SubscribeToPaneRendersMsg` field 4, so no message and no numbering changed.

### `zellij action --json` answers the mutations too

```
$ zellij action --json new-tab
{
  "tab_id": 2,
  "pane_id": "terminal_4",
  "handle": "hefty-magpie"
}
$ zellij action --json toggle-floating-panes
{}
```

The output convention said `--json` was the direction for the mutations and not yet a promise. It is
one now: a verb that reports a record answers with one object, a verb that reports nothing answers
`{}`. The flag goes in front of the verb, because the seven verbs already answering in JSON own the
trailing one — for those seven both positions are the same call. A verb that prints a payload rather
than a record (`dump-screen`, `dump-layout`) exits **2** and says so, read from the same `prints:`
table `setup --dump-surface` publishes. The whole feature is in the client's printer, so nothing on
the wire moved.

### `dump-screen` sweeps many panes in one invocation

```
$ zellij action dump-screen --all | jq -r 'select(.content | test("error")) | .handle'
brisk-heron
```

`--pane-id` repeats, and `--all` is every pane the session has. A caller reading a session over ssh
pays for the **round trip**, not for the dump: a sweep of ten panes was ten ssh invocations and ten
connections to read ten screens the session already held. It is now one of each.

One pane is what it always was, byte for byte — the shape follows what was asked for, so it becomes
JSON only when more than one pane is named or with `--all`. A line per pane rather than one array, so
a megabyte `--full` sweep can be read while it is still running. A named pane nobody answers to costs
that one pane and exits **2** at the end, with the panes beside it still dumped. No new action, no
message tag, nothing on the contract.

### `zellij pipe` answers, and gives up when nothing does

```
zellij pipe --name build-done -- ok               # gives up after 30 idle seconds
zellij pipe --timeout 0 --name build-done -- ok   # waits however long it takes
```

Two faults, each hiding the other. **Every CLI pipe reported an error it had no reason to report**:
`Action::CliPipe` drops its completion channel on purpose, and the route thread read that as "the
action reported nothing", so `zellij pipe` exited **2** about fifty milliseconds in whether or not
anything was wrong — ahead of the plugin's real answer. **With that gone, the hang underneath it is
reachable**: only a plugin that received the message can unblock a pipe, so a session with none
listening never answered and the client waited forever.

`--timeout` bounds the wait: exit **2**, and a sentence naming the pipe. The window is **idle time**,
not a budget for the call, so `tail -f | zellij pipe` is unaffected and a streaming plugin restarts
it on every send. It defaults to 30 seconds rather than to nothing, because a flag-only patch would
have turned today's fast wrong exit into an unbounded hang for every existing caller. The flag never
reaches the session.

### `--cwd` reaches a pane that runs no command

```
$ zellij action new-pane --cwd /etc          # opened wherever the focused pane was; now /etc
```

A pane that runs a command carries its directory inside `RunCommandAction`. A pane that runs no
command has no such struct, and none of the four `Action::New*Pane` variants had a field for one — so
the CLI resolved `--cwd`, built the action and dropped the value on the floor, silently. Every
command-less placement was affected: plain, `--floating`, `--stacked` and `--in-place`.

The fix is one new action rather than a field on four upstream messages: `Action::NewShellPane`,
tag **173** in the fork's reserved block. No `--cwd` still means "wherever the focused pane is" —
nothing is filled in on the caller's behalf. `--borderless` now reaches `--stacked` too.

### `input_while_scrolled`: typing into a scrolled pane no longer eats the key

Upstream 0.45 puts the client into Scroll mode whenever the focused pane is scrolled, and the mode
then decides what a key means — so a printable key typed into a scrolled pane is **discarded**, and
`e` and `s` are worse than discarded because the scroll keymap binds them to `EditScrollback` and
`EnterSearch`. Read a log, scroll up, start typing: the first characters vanish and the fourth opens
an editor.

| Value | Implicit mode switch | A key typed into a scrolled pane |
|---|---|---|
| `scroll-mode` (default) | yes, as upstream | resolved in Scroll mode; an unbound key is discarded |
| `jump` | no | clears the pane's scroll, flushes the held output, then reaches the pty |
| `stay` | no | reaches the pty; the viewport does not move |

The default is the upstream behaviour, so an unset config is 0.45 exactly. `jump` is the 0.44 feel.
The option governs only the *implicit* sync, both halves of it — an explicit `SwitchToMode "Scroll"`
behaves identically under all three. It is a **top-level** key, so rollout is free.

### Each pane keeps its own scroll and search mode across focus changes

Scroll position, search term, results and toggles are already per pane; the mode flag was the only
thing that was not, so searching a log in one pane and glancing at another left the pane where you
put it while your mode went elsewhere. Upstream
[#5419](https://github.com/zellij-org/zellij/issues/5419) and
[#5470](https://github.com/zellij-org/zellij/issues/5470), neither with a maintainer reply.

Only the scroll/search family is remembered — every other mode is a transient menu that belongs to
the client. Focusing a pane that remembers nothing takes you back to the default mode. The memory is
per pane rather than per (pane, client), matching the state it sits beside, and it lives on the pane,
so a closed pane's mode dies with it. Nothing crosses the plugin API.

### Closing a tab with more than one pane asks first

The tab-mode close key and `zellij action close-tab` used to be the same button. One is pressed by
somebody who meant to close a *pane* and reached one menu too far; the other is typed on purpose.
Only the key is gated now, by a new bundled plugin, `zellij:confirm-close-tab`.

A tab with one pane closes with no prompt at all — the plugin decides in `load`, before it renders a
frame. A tab with more than one asks: `close tab? 3 panes open  [y/N/p]`, where `p` closes only the
pane you were in, which is what the miss-press usually meant. The CLI is exempt structurally rather
than by a check: `close-tab` confirms client-side before the action is ever sent, and `--yes` still
means what it meant.

### The keybind bar says whether Full Disk Access is still there

```
 Ctrl +  LOCK  PANE  TAB  RESIZE        cpu 12% | ram 7.0/23G | disk 412/931G | fda no
```

A Mac that loses Full Disk Access loses it quietly, and the first sign is whatever needed the
permission failing hours later. The reading rides the one `/bin/sh` the vitals cluster already runs
every ten seconds, so there is no new spawn and no new permission. The question is a real `open` of
the TCC database, because `access(2)` reads only the permission bits and answers "readable" on a
machine holding no grant. Three answers: `fda ok`, `fda no`, and nothing at all where the question
does not apply — so a Linux cluster is byte-identical to what it drew before.

### The web server takes a token in a header, and keeps an active session alive

Three changes to how an **existing** session token may be presented. None widens who can get one:
`/command/login` still takes an auth token `zellij web --create-token` made and still refuses
anything else.

- `Authorization: Bearer <session token>` is accepted where the cookie was the only way. The cookie
  is still tried first, so nothing about a browser changes.
- A login body carrying `"headless": true` returns `session_token` in the response and sets no
  cookie, for a caller with no jar. A browser login is untouched and its body still carries no token.
- A short-lived token now lives five minutes from its **last use** rather than from the login, so an
  open session is no longer logged out mid-use. It cannot resurrect an expired token, it leaves
  `remember_me` tokens alone, and it writes only in the last half of the window.

### Three config blocks warn on a key they do not know

An unknown TOP-LEVEL key in `config.kdl` has always been ignored, which is what lets a config reach
every machine before the binary that reads it does. A block that parses its own children lost that
property: an unknown child failed the **whole file**, not the block. `managed_session` and
`launchd { env }` each paid that price.

`session_service`, `pane_privacy` and `resurrect_command_hints` now **keep, log and ignore** a name
this build does not know, at every depth. Only the unknown-*name* case is softened: `on_unknown_cwd
"withold"` still fails the config, and so does a hint that names no `match`, `env` or `resume_args`.
A privacy setting silently dropped is worse than one that refuses, and the operator who wrote it
meant it; an unknown name means the opposite. The warnings print as one run under `setup --check` and
log at `warn` for a running session, and an ignored entry is not written back by `setup
--dump-config`.

## Changed

### Synchronised output is assumed, not withheld until a terminal proves it

Upstream queries the host for DEC private mode 2026 at client startup, and until the reply lands it
falls back to a `TERM` match naming exactly one terminal — alacritty. The query works; the default it
falls back on is what is wrong. Anything that supports the mode but never answers a DECRQM, and
anything at all during the startup round trip, renders unsynchronised. Zellij sends only the lines
that changed and clears its buffer the moment it has, so a frame arriving in pieces is not a flicker:
the terminal draws part of it at the wrong cursor position and nothing re-sends those lines. Over SSH
that drift accumulates into duplicated pane borders until a detach forces a full redraw.

Every terminal but alacritty now starts on the CSI form, and the host's DECRPM reply is still the
authority in both directions. The cost of being wrong this way is sixteen bytes a frame that nothing
acts on; the cost of being wrong the other way is a corrupted screen. The remote-attach client needs
it most — its binding is immutable and never sees the reply at all. `ZELLIJ_SYNC_OUTPUT` (`off`,
`csi`, `dcs`) is the escape hatch for a host that mishandles the mode and stays silent about it.

Upstream rejected the same two-line flip in
[#4694](https://github.com/zellij-org/zellij/pull/4694), on the argument that the CSI path was never
the default — which is untrue on a replying terminal.

### A generated unit carries the `PATH` of the shell that enabled it

The unit used to get the directory of the binary it execs, followed by the platform default, on the
reasoning that the directory a binary was found in is one a machine keeps terminal software in.
`pin_exe` makes that false: the pin directory holds zellij and **nothing else**, so the
package prefix drops out along with `~/.local/bin` and every npm or bun global bin. A server started
from that unit cannot resolve `claude`, `codex` or `opencode` — and every layout `command` pane,
`zellij run --`, `copy_command` and resurrected command fails with "command not found" beside an
interactive pane that works, because the rc chain fixes the *shell's* `PATH` and never the server's.

The `PATH` is now **recorded rather than reasoned about**, the same principle as the state root and
the binary path: resolved once, at `enable` time, in the environment that ran it. The binary's own
directory leads, order is preserved and repeats are dropped, and an environment with no `PATH` falls
back to the platform default. It stays a default, so `launchd { env { PATH … } }` and `systemd
{ service "Environment=PATH=…" }` still replace it.

### A payload on the command line is the whole pipe

`zellij pipe -- payload` got its answer and then **blocked forever** on any stdin that is neither a
terminal nor ever at EOF — which is the usual case for a program that shells out, since a command run
over ssh or a child of a long-lived server inherits a handle that stays open for the life of the
parent. `--timeout` could not end it, because the read is outside the window by design. `< /dev/null`
was the only cure, and a caller should not have to know that.

A payload given on the command line is now a reason not to read stdin, the same as a terminal is.
Nothing changes for a pipe that means its stdin: `echo data | zellij pipe --name logs` still reads to
EOF. The one behaviour traded away is `echo data | zellij pipe --name n -- payload`, which used to
send both and now sends only the payload.

## Fixed

### One session that will not answer no longer hangs every command that lists sessions

A server whose teardown wedges keeps its listening socket, and a socket that accepts a connection and
then says nothing used to hang **every** command that enumerates sessions — for every session in the
directory, not just its own. `ls`, `attach`, `delete-session`, `kill-session`, `session up` and the
"did you mean" suggester all go through `get_sessions`, which blocked in `recv` with no deadline. One
bad tab close took session enumeration out machine-wide until the pid was killed by hand. Measured
before the patch: `zellij ls` had not returned twenty seconds later and never listed the healthy
session beside it. After: 2.1 seconds.

Four changes, because the failure has four parts.

- **The probe is bounded** — two seconds, and silence is "not a session", which is the answer a
  refused connection already got. The unresponsive socket is deliberately left in place: unlinking it
  would orphan a server whose panes are still running.
- **The accept loop stops making clients once the session is over.** Every connection accepted after
  the main loop broke became a client id, a router thread and a sender thread with nobody to serve
  them. Under a storm through a last-tab close, the census two seconds later went from forty
  abandoned sender threads to none.
- **A pipe whose session went away stops instead of spinning.** `--timeout 0` read a closed socket,
  got nothing, and read again — a spin at 100% of a core for as long as the process lived.
- **Every wait in teardown is bounded**, five seconds per join, so one stuck thread no longer means a
  server that lives forever holding a socket that answers nothing.

Reported upstream as [#5440](https://github.com/zellij-org/zellij/issues/5440); nothing has landed
there.

### The server raises its own open-file limit, and a refused connection is not fatal

A five-day-old session with about twenty-five tabs died and took every pane with it, on
`err Os { code: 24, … "Too many open files" }`. Two faults.

**The soft limit was whatever the shell handed over**, and macOS still defaults that to 256. A
session's descriptor use grows with what is in it, so a long-lived one walks into the ceiling and
everything downstream starts failing at once. The server now raises its own soft limit at startup to
`min(hard limit, 10240)`, never lowering one that is already higher and never touching the hard
limit. Unix only.

**A connection that could not be accepted killed the session** — the listener's error arm was
`panic!`, and the panic hook takes the server down, so one client's failed attach cost every pane. It
now logs and backs off, 50 ms doubling to a ceiling of one second, and the log thins after the first
five. Reported upstream as [#5474](https://github.com/zellij-org/zellij/issues/5474).

### A client whose terminal dies detaches instead of crashing

Kill the terminal window a client is attached to, or drop the ssh connection carrying one, and the
tty starts answering EIO. The client panicked on the way out, because its teardown unwrapped calls
only a live terminal can satisfy — `unset_raw_mode` on Linux, the goodbye write on macOS. All
thirteen unwrapped calls in the five teardown blocks are now tolerant, and the errors are logged
rather than discarded. The startup counterparts are deliberately left alone.

The panic was worse than it looks: `handle_panic` printed with `println!`, which itself panics when
stdout is gone, and a panic inside a panic hook **aborts**. That is the `Abort trap: 6` in the crash
reports. The render path is the half that mattered for the session — a render landing on a dead tty
killed the client before it had sent `ClientExited`. A failed render now sets the client's own detach
in motion without breaking out of the loop, which would have deadlocked the router against a full
channel.

### `confirm-close-tab` closes one tab, not one per attached client

Zellij loads a plugin once per connected client and runs `load` in every one of them. Without a
guard, one keypress closed one tab per client: the instances run in turn, and the second woke to a
session that had already lost the first tab, found its client focused on the *next* one and closed
that too. With two tabs and two clients that emptied the session and took the server down with it.
Only the instance whose client pressed the key may act; every other instance is inert for the rest of
its life.

### A `subscribe` feed does not narrow when somebody attaches

Two panes in two tabs. With nobody attached, both feeds ran; the moment a human attached, the pane in
the tab they were not looking at went silent, and came back when they switched tabs. A consumer
therefore got *more* data while nobody was watching, and the feed rearranged itself around a human's
tab.

The two delivery paths read from different places — the render report, which carries only what was
rendered, and a direct per-pane query with nobody attached. There is now one path: it takes the
render report when there is one and queries whatever the report is missing. Floating panes are
covered by the same fix, and a subscribed plugin pane is now read through a client rather than
served empty.

### A plugin's `BeforeClose` handler gets a window to finish in

`Event::BeforeClose` is a plugin's one chance to say anything on the way out, and the session did not
wait for it: `cleanup` queued each handler on a worker thread and returned, and the background-jobs
thread that dispatches a handler's `web_request` was told to exit at the same moment as every other
one. On a fast teardown the handler managed nothing at all.

`cleanup` now waits up to **two seconds** for the queued handlers, background jobs are told to exit
last, and that thread waits up to three seconds for web requests already in flight. A pane closing on
its own is unchanged — the wait is in `cleanup`, which runs once. `SIGKILL` stays lossy and always
will.

### `session status` ends quietly when the reader stops reading

`zellij session status mysession | head -3` panicked on the fourth `println!`, because `head` had
closed the pipe and `println!` has one answer to a failed write. A reader doing something entirely
ordinary produced a crash report, a `101`, and a stack trace in the middle of a script. The report now
goes through a handle: `BrokenPipe` exits **0** and says nothing, any other write error is reported on
stderr and exits 1. It deliberately does not touch the process-wide `SIGPIPE` disposition — this
binary is also the server and every pane in it.

### Eight smaller ones

- **`is_focused` names a client that is still here.** A pane was reported focused for a client that
  had detached, and on a session nobody had ever attached to. `pane_info` now applies the connected
  set to the same map, so a re-attaching client still lands where it left. Upstream
  [#5468](https://github.com/zellij-org/zellij/issues/5468).
- **A write that names a pane leaves every viewport alone.** `write --pane-id` sent a `ClearScroll`
  that resolved to whichever client the server could find, so a script writing into another tab
  dropped a bystander's scrollback to the bottom. Upstream
  [#5476](https://github.com/zellij-org/zellij/issues/5476).
- **`go-to-tab-by-id` answers a miss with nobody attached.** It asked about the client first, so it
  reported its miss only while somebody was there.
- **A stack list obeys `top_only`.** `render_stack_list_headers` builds its own
  `PaneContentsAndUi` and never called `set_top_only_frames` — the one place the frame style visibly
  did not hold.
- **A plugin's `.wasm` watch goes away when the plugin does.** Watches, debouncer cache entries and
  the watched-file map grew for the life of the server. The watch belongs to the file rather than to
  the plugin id, so it is released when the last instance loading it, running it or failed on it is
  gone.
- **The tab-mode close hint follows the key that launches the prompt.** `x  Close` dropped off the
  hint line when `x` was rebound, because the status bar matches the action *list* a key is bound to
  and the binding is now a `LaunchOrFocusPlugin`. Fixed in the status bar as a fallback, and in
  `slim-keybinds` and `compact-bar` by classifying that launch as `ActionType::CloseTab` so the key
  is labelled `close` and gathered into the existing hint.
- **Doctor unlocks the keychain on the Apple-cert rungs too.** `ZELLIJ_KEYCHAIN_PASSWORD` reached
  `security` only as `-k` on `set-key-partition-list`, which runs only for the certificate we mint —
  so a machine signing with an Apple Development or Developer ID certificate ignored the variable
  entirely, and a locked keychain refused the key while the remedy printed beside the refusal told
  the reader to set the one thing the run had ignored.
- **The plugin API doc comments say what the spike had to learn the hard way.** `pipe_name` is
  renamed `pipe_id` on the three pipe-answering shims, because the session keys its pipes by id and
  answering under the `--name` the caller typed reaches nothing; `web_request` and
  `request_permission` say that a request issued before `WebAccess` is granted is dropped in silence;
  and `PaneClosed` and `PaneExited` say they do not arrive in a fixed order.

## Operator notes

- **Tab-mode `x` prompts now.** The binding lives in the binary's own `default.kdl`, so nothing has
  to be rolled out: an older binary keeps `CloseTab`, a newer one gets the prompt. A user
  `config.kdl` that already overrides tab-mode `x` keeps its own binding and **must not** be
  rewritten ahead of the binary — `zellij:confirm-close-tab` is a plugin location an older build does
  not have.
- **The softened config blocks help from this build forward, not backward.** A machine still on
  ≤ nkmk.17 fails the whole config on an unknown child of `pane_privacy` or
  `resurrect_command_hints`, and ≤ nkmk.16 does the same for `session_service`. Check the oldest
  binary in the fleet before seeding a nested key. `input_while_scrolled` is **top-level** and free
  to seed on every machine now.
- **Unit drift, and a restart with it.** A unit enabled before this release carries the old narrow
  `PATH` and nothing rewrites it in place. Re-record with `zellij session enable <name>`, then
  `zellij session restart <name>` — a server's `PATH` is fixed for the life of the server, so the
  rewrite changes nothing until the session is created again.
- **Against a stock server, a command-less `new-pane` now does nothing.** Tag 173 means nothing
  there, so the server decodes an `Action` with no type set and makes no pane. It used to work and
  ignore `--cwd`. Naming a command, or `--blocking`, still works.
- **`zellij pipe` has a 30-second idle default.** A caller that wants the old unbounded wait must
  pass `--timeout 0`. And `echo data | zellij pipe --name n -- payload` now sends only the payload.
- **`dump-screen` changes shape only when asked for more than one pane.** One `--pane-id` prints the
  bare content exactly as before; two or more, or `--all`, prints a JSON object per line. A script
  that builds `--pane-id` from a list must know that a list of one answers differently from a list of
  two.
- **The fd-limit raise is unix-only** and never lowers a soft limit that is already higher. macOS is
  where it bites; Linux raises itself a second into session startup, which is why this was never a
  Linux crash.
- **`zellij-mac-setup` refuses to run when it predates the installed binary** (exit 3). It expects
  `SCRIPT_FOR_RELEASE=0.45.0-nkmk.18`.

## Upgrading

- Macs: `brew upgrade zellij-nkmk`, then `zellij-mac-setup`, then `zjr`.
- Linux: `session enable` once after upgrading to re-record the `PATH`, then `session restart` to
  create the session under it.
