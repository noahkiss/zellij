# v0.45.0-nkmk.8

- **Upstream base:** `f42ca3c79` on upstream `main` (workspace version `0.45.0`) — unchanged since
  nkmk.1
- **Range:** `v0.45.0-nkmk.7..main` (3 commits)
- **Released:** 2026-08-15

Two fixes. **nkmk.7's signing fix was proven insufficient the first time it met real Macs**: it made
`session doctor --fix` reach the Apple rungs, and the rungs then wrote a signature that satisfies no
requirement while reporting success. nkmk.8 fixes what it wrote and, more to the point, makes doctor
check the binary rather than the text it just handed `codesign`. The second fix is unrelated: the
`zellij mcp` server emitted a tool list that a 2026-era MCP client refuses, so a connected server
delivered no tools at all.

## Fixed

### Verify the signature, and read the team id off the certificate

Three faults, found on two real Macs running nkmk.7, each behind a rung no test machine had reached.
The first two were invisible for the same reason: doctor asked whether the requirement **read**
correctly, never whether the binary **satisfied** it.

**The team id came off the identity's name.** On a Developer ID Application certificate the
parenthesised code in the CN and the subject `OU` are the same string — which is exactly what let
this ship twice. On an **Apple Development** certificate they are not. So that rung signed, wrote
`certificate leaf[subject.OU] = "<per-developer id>"`, and produced a signature that fails its own
designated requirement: a pin holding no TCC grant at all, reading exactly like one that does. The
team id now comes from the certificate — `security find-certificate -c <name> -p` into
`openssl x509 -noout -subject`, parsed for the `OU` in both LibreSSL's `/OU=V/` and OpenSSL 3's
`OU = V,` spelling, since either binary may be first on `PATH`. A certificate that cannot be read
yields no team id, and a rung with no team id writes **no** requirement and takes the CN-anchored
one `codesign` derives. That is the fallback, not the default: the derived requirement survives
every rebuild and breaks only on a reissue, while a requirement built from the wrong field voids
the grant immediately.

**Nothing verified the signature.** `codesign -v` returns 0 on a pin that `codesign -v --verbose=2`
rejects with `does not satisfy its designated Requirement` and exit 3 — the designated-requirement
check is what the second verbosity level adds. Verification is now
`--verify --strict --verbose=2`, and it matches the message as well as the exit status, because the
exit status is the half already caught reporting success wrongly. The same check now runs against a
pin doctor did **not** sign, before it is called healthy. Without it a mis-signed pin was reported
`Already correct` on every later run, so a machine in that state could never repair itself; a pin
that fails verification is now signed again.

**The minted bundle carried an empty passphrase**, which Apple's importer cannot read. The
algorithms fixed in nkmk.7 were necessary and not sufficient: with the same key, certificate,
algorithms and LibreSSL, `-passout pass:` fails MAC verification and `-passout pass:zellij` with
`-P zellij` imports. The passphrase is a constant in the source next to the file it opens — it
protects nothing, and the 0700 directory and 0600 file still do. A bundle that will not import is
now set aside as `id.p12.broken-<epoch>` and minted again, behind **two** gates: the import error
must name the proven case, **and** `security find-certificate` must find no such certificate in the
keychain. Reusing one forever meant a machine that failed once could never be repaired by any later
release; minting on any other failure would be worse, because a locked keychain fails an import
while holding the certificate every grant on that machine names. `find-identity` cannot be the
second gate — it folds "never imported" together with "will not answer", and the one caller has
already had that answer.

**Discovery missed our own certificate.** `find-identity -v` filters on validity, and validity is a
trust decision, so a certificate we minted is listed as `(CSSMERR_TP_NOT_TRUSTED)` and the summary
reads `0 valid identities found` on a machine that holds it and signs with it fine. A second
listing without `-v`, filtered to our own common name, fixes it. Not `add-trusted-cert`: that would
change what Gatekeeper accepts machine-wide, need an administrator, and buy a grant nothing —
requirement evaluation ignores trust unless the requirement says `trusted`, and ours never does.

A rung reached by falling from the one above it, whose team id could not be read, now says so in the
follow-up. It writes no requirement, so the derived one is not what the rung above would have
written, and a user told to re-grant is owed the reason.

### The MCP tool list carries the cache metadata `2026-07-28` requires

A client that opens with `server/discover` — Claude Code 2.1.233 does — is told this server speaks
`2026-07-28` and sends `tools/list` in that era. The reply carried neither `ttlMs` nor `cacheScope`,
which that era's result schema requires (SEP-2549), so the client refused the whole list: the
connection succeeded and **not one of the seven tools reached the model**, which reads as a missing
server rather than a protocol fault. A client that negotiates `2025-11-25` through `initialize`
never saw it, which is why the server looked fine everywhere it was tested.

rmcp models both fields as optional, because one Rust type has to serve the older revisions too, and
`ListToolsResult::with_all_items` leaves them unset — so the omission compiles. The fields are now
set rather than the advertised protocol versions narrowed: the server conforms to the era it claims
instead of opting out of one it otherwise implements correctly. A test asserts both are on the wire.

Affected clients are the ones that discover rather than negotiate — Claude Code 2.1.233 and later.
Older clients were never broken and see no change.

## Changed

### The detached-session notes in `AGENTS.md` describe the current binary

Documentation only, no behaviour. Two of the three warnings had been overtaken by the class-2 exit
guards added through nkmk.6 and pointed automated tests the wrong way. Geometry in a never-attached
session is not placeholder — the layout pass runs, and panes and stacks are self-consistent against
a default 50×50 viewport rather than a client's real terminal. And focus does not silently fall back
to the first tab: `move-tab` with no `--tab-id`, `focus-next-pane`, `new-tab` and `dump-screen` with
no `--pane-id` each name what is missing, exit 2, and change nothing.
