# v0.44.3-nkmk.10

- **Upstream base:** `v0.44.3`
- **Range:** `6f1802eef..518a8d5f2` (26 commits)
- **Released:** unreleased

The largest release of the fork so far. Three themes run through it:

1. **Nothing fails silently.** A dropped session, an empty list, a pane too short, a config that
   no longer matches the installed unit — each now says so where the user is looking.
2. **Resolve once, record the answer.** A launcher's environment is not the calling shell's, so
   paths are resolved at `enable` time and written into the unit instead of re-derived at run time.
3. **The session manager can reopen anything.** Live sessions, other clients, and the snapshot
   archive are all reachable from inside a session.

Full detail for every item is in [FORK.md](../FORK.md); the section links below point at it.

## macOS file access

| Change | Effect |
|---|---|
| The probe runs off the main thread | A pending consent dialog no longer blocks server startup |
| FDA claim corrected | The docs no longer claim the probe registers a Full Disk Access client |
| The warning resolves the path | The message names the file TCC keys the grant to |

`probe_protected_locations()` ran on the server's main thread. A protected location with no
decision on record blocks inside the `open` until someone answers the dialog, so the session never
appeared — about 100 seconds on one machine, and once until reboot. Nothing reads the probe's
result, so it now runs on its own thread. `probe_protected_locations_now()` keeps the blocking
body.

This gives up an ordering guarantee: panes spawn while a decision may still be pending. TCC
coalesces, so two processes touching the same protected directory both wait on the one dialog and
neither is refused.

FORK.md and the probe's own comment said the FDA-gated read registers the client in the settings
pane. Four controlled tests do not support it, and both texts now say only what was demonstrated.
The Files & Folders half is unchanged and still works. The warning also named the wrong path:
`current_exe()` returns the symlink a package manager puts on `PATH`, while TCC keys the grant to
the resolved target.

See [macOS decides about file access at server start](../FORK.md#macos-decides-about-file-access-at-server-start-not-weeks-later-macos-only).

## A pinned copy of the binary (`pin_exe`)

```kdl
session_service {
    pin_exe true                        // the platform's canonical location
    pin_exe "/opt/zellij/bin/zellij"    // or a path you name
}
```

A package manager installs each release into its own versioned directory, so the path a launcher
was told about is the path the next upgrade deletes. On macOS it costs more than a broken unit: TCC
keys a path-based client on its absolute path, so every upgrade is a client the system has never
seen, holding none of the grants the last one earned.

`pin_exe true` installs a real copy of the running binary at the platform's canonical per-user data
directory (`~/Library/Application Support/zellij/bin/zellij`, `$XDG_DATA_HOME/zellij/bin/zellij`)
and the generated unit names that path. `pin_exe "<path>"` names one instead. Unset by default, and
unset is the whole feature off.

Measured on one machine: a symlink never holds a grant, because macOS resolves it and records the
target. A real file keeps its grant when a different build is written over it, across a tccd
restart and a reboot. So the refresh writes over the same file and never unlinks and replaces it.

| Command | What it does now |
|---|---|
| `session enable` | Installs the copy **before** writing the unit that names it |
| `session up` | Refreshes the path the **installed unit** records, never a re-derived one |
| `session status` | Names the config path and the unit path, and exits non-zero when they differ |

Whether to write at all is decided by build identity, not a timestamp. Same build, nothing is
written — which is every pass but the first after an upgrade, on a command a watchdog runs every
minute over a 40 MB binary.

See [A pinned copy of the binary](../FORK.md#a-pinned-copy-of-the-binary-pin_exe).

## Build identity

`compare_builds` decided identity by device and inode, so a **copy** of a binary compared
`Different` and every client printed "session … is running a different build". Pinning the binary
makes that copy the normal case, and a consumer driving `zellij action` sees the warning on every
call.

- Inodes stay as the fast path. Where they differ, the linker's stamp decides: the Mach-O `LC_UUID`
  or the GNU build-id note. Both sit in the first few kilobytes, so the reader parses the header and
  the load commands or `PT_NOTE` segments — never the whole file.
- The note is found through the program headers, not by section name, because `strip` may discard
  sections and never discards segments.
- Absent evidence reports `Unknown` and says nothing. A wrong "your session is stale" sends someone
  to restart a session that did not need it.
- Linux release builds now carry a build-id. `rustc` passes no `--build-id`, so `.cargo/config.toml`
  asks the linker for `--build-id=sha1` on `cfg(target_os = "linux")`. That does not match
  `wasm32-wasip1`, so the bundled plugins are untouched.
- Verified on a `--release` build with `strip = true`: the `.note.gnu.build-id` **section** is gone,
  the `PT_NOTE` **segment** carrying it is not, and the fork's reader returns the id `readelf` does.
  The release workflow passes `rustflags: ""` to the toolchain action, where an empty string means
  do not export `RUSTFLAGS` at all — Cargo drops config-file rustflags whenever that variable is
  set. The empty string is load-bearing and is now documented as such.

See [A warning when the running session is a different build](../FORK.md#a-warning-when-the-running-session-is-a-different-build).

## Session service

### Creating a session

| Fix | Symptom it removes |
|---|---|
| `flock` on `session up` | A hand-typed `restart` racing the watchdog tick created two servers for one name, and every later `up` refused until one was killed by hand |
| Watchdog armed first | `enable --now` failed on the service, so the timer that would have retried was never enabled — on exactly the machine that needed it |
| Backoff while waiting | The gap doubles from 50 ms to 1.5 s over the same 10 s timeout: about eight times fewer `ps` forks on a failing machine, no measurable difference on a healthy one |
| Dangling `SSH_AUTH_SOCK` dropped | A stale agent socket made every agent-backed command fail with "Permission denied (publickey)" for the session's whole life |
| `copy_command` warning | `copy_command` runs in the server, so a launcher gives `wl-copy` or `xclip` no display and copy fails into `log::error!`. Not warned on macOS, where `pbcopy` needs neither variable |

Nothing gives up early and nothing escalates. The failure is already reported to the journal or the
log the plist names, and a watchdog that switches itself off is the one state a person cannot
recover from without a shell on the machine.

`enable` and `disable` now collect their failures instead of returning on the first one.

### Finding the right directory

- **`zellij ls`** — the empty case prints the resolved socket directory, then the derived
  alternatives, and says a directory nothing here was told about cannot be on that list.
  `zellij session up <name>` scans the process table and does see such a server.
- **systemd unit directory** — `enable` and `status` read `XDG_CONFIG_HOME` out of
  `systemctl --user show-environment` instead of deriving it from the calling shell. A unit written
  into the shell's directory is a file the manager never looks at. Both directories are named when
  they differ. A quoted value is left unread rather than half-unquoted, and a machine with no user
  manager falls back to the derived path.
- **State root** — the snapshot archive and `restart.log` hang off `$XDG_STATE_HOME`. A `down` typed
  in a pane archived to one root while the launcher's `up --restore latest` looked in another, so
  the session came back from the layout rather than the saved shape, with nothing failing and
  nothing warning. `enable` now writes the absolute root into the unit: `Environment=` for systemd,
  an `EnvironmentVariables` entry for launchd. It is a default, so a config that sets its own
  replaces it, and it is absent when the enabling environment has no absolute one.
- **System unit directories** — the installed-job scan reads `/Library/LaunchAgents`,
  `/System/Library/LaunchAgents`, `/etc/systemd/user`, `/run` and the two lib paths as well as the
  user's own. A nearer directory shadows a file of the same name, matching the init systems'
  precedence. `enable` and `disable` still write only to the user's directory. A raw-bytes check for
  `session` runs first, so Apple's several hundred binary plists cost one read each rather than a
  `plutil` fork.

### `session_service` and drift

- **Arrays and dictionaries.** A launchd key may now carry a container. Every child named `-` makes
  an array, anything else makes a dictionary, and a block mixing them is refused rather than
  resolved one way. Emission is recursive and indents by depth. `WatchPaths`, the dictionary form of
  `KeepAlive` and `StartCalendarInterval` are now expressible. The guard against pinning `TMPDIR` or
  `ZELLIJ_SOCKET_DIR` reads every string at any depth.
- **Scheduling keys are defaults.** `RunAtLoad`, `StartInterval` and `LimitLoadToSessionType` were
  the generator's outright, so an extra of the same name was refused — an agent on any interval but
  60 s could not be reproduced. They are now defaults: a config entry replaces them, the key appears
  exactly once, and nothing changes when nothing configures them. `Label`, `ProgramArguments` and
  `EnvironmentVariables` stay the generator's, because those three are what the unit is. A test
  asserts every key the hand-written agents used is settable.
- **Drift detection.** Edit the config and the loaded job does not change with it. `status` gains a
  `drift` line and counts drift against its exit code; `up` reports it once per invocation, so it
  reaches an unattended machine through the journal or the log. Silent unless something zellij wrote
  is installed **and** differs. The remedy is `session enable`, not a reload by hand: launchd needs
  `bootout` then `bootstrap`, while `launchctl kickstart` restarts from the definition launchd
  already holds. A job installed under another name is not compared.

See [The config and the installed unit are compared](../FORK.md#the-config-and-the-installed-unit-are-compared)
and [Extra unit directives from the config](../FORK.md#extra-unit-directives-from-the-config-session_service).

## Session manager

### It says why the list is empty

The list is polled once a second and `Err(_) => return false` threw the message away, so a failing
poll left an empty list forever with nothing to distinguish it from a machine with no sessions. The
server's message now renders where the list would be, and is logged. It is a plain line, not the
error modal — the modal swallows the next keypress, and a failure that re-arms every second would
make the plugin untypeable. A poll that succeeds and returns nothing gets a line too.

Behind that: a session with a socket but no readable, parseable `session-metadata.kdl` was dropped
from the server's scan silently, while `zellij ls` — which reads the sockets alone — kept listing
it. The scan now warns, naming the session and the reason, gated on a map of currently-dropped
sessions so a once-a-second poll logs one line per state change rather than per pass. The map gates
logging only; scan results are as deterministic as before.

Both list views also name the count they cannot draw when the pane is too short, and say nothing
when the list is genuinely empty or a filter matched nothing.

### `Ctrl+l` — the client list

Shows every client attached to the current session: its id, the pane it is focused on, and what
that pane is running. `d` detaches the selected one. Until now the only answer to a second client
was `Ctrl+x`, which disconnects all of them.

A row identifies a client by what it is looking at — the laptop is the one in `nvim` — and both
fields were on `ClientInfo` already. The current client is listed, marked, and refused: `d` on it
says to use the session's own detach key. The list polls once a second and clears on open rather
than showing the previous answer.

### `Ctrl+e` — the snapshot picker

A chooser over every session shape worth reopening, live or archived, with the tabs and panes of
the selected one beside it.

| Key | Action |
|---|---|
| `ENTER` | Attach to a live session, or rebuild an archived one |
| `Ctrl+r` | Restore a snapshot under a different name |
| typing | Filter by name |

The preview is the point. The archive was reachable only from another terminal, as a list of ids
and timestamps, and `snapshot show` answers "what is in this one" by printing a whole layout file.

Restoring over a running session is refused, and the row says so before the key is pressed. The
server refuses it again, because the picker's list is a poll old and the failure it prevents is
silent — the switch would attach to the running session and discard the layout. A layout that no
longer parses is refused the same way. The archive is re-read once a second, with the selection
carried by name and id so an arriving snapshot does not move the row under the cursor. Below 60
columns the preview is dropped rather than squeezed.

`Ctrl+e` is not a mnemonic and none was left: `s`, `h` and `a` switch modes before a key reaches the
plugin, and `r`, `d`, `x`, `w`, `k` and `l` are bound inside it. The help line carries the label.

See [The session manager picks a session out of the archive](../FORK.md#the-session-manager-picks-a-session-out-of-the-archive).

## Plugin API

New tags only. Nothing is reused or renumbered, so a plugin built against an older API keeps
working.

| Addition | Tag | Permission |
|---|---|---|
| `PluginCommand::DetachClients(Vec<ClientId>)` | `CommandName = 215`, payload `164` | `ChangeApplicationState` |
| `PluginCommand::ListSnapshots` | `CommandName = 216`, no payload | `ReadApplicationState` |
| `PluginCommand::RestoreSnapshot { snapshot_id, session_name }` | `CommandName = 217`, payload `165` | `ChangeApplicationState` |
| `Event::ListSnapshots(Vec<SessionSnapshotInfo>)` | `EventType = 47`, payload `41` | — |
| `Event::SnapshotRestoreFailed(String)` | `EventType = 48`, payload `42` | — |

- **`DetachClients`** sends the ids to the same `ServerInstruction::DetachSession` that
  `Action::Detach` uses, so a detached client keeps its session exactly as if it had pressed its own
  detach key. The API had `Detach` and `DisconnectOtherClients` and nothing in between.
- **`ListSnapshots`** is a request, not a field on `SessionUpdate`: reading the archive walks a
  directory tree and parses every saved layout, and `SessionUpdate` is broadcast to every subscribed
  plugin about once a second. `SessionSnapshotInfo` carries the sidecar and the layout both, so a
  snapshot whose layout no longer parses still reports its size and arrives with `layout_error` set
  rather than reading as an empty session. A directory holding no `session-layout.kdl` is left out,
  and warns — gated by the same map as the dropped-session warning. The read runs on the plugin
  thread.
- **`RestoreSnapshot`** is `zellij snapshot restore` reached from inside a session. The layout is
  trial-parsed before the switch, since once the client has been told to switch there is no screen
  left to report a parse failure. Restoring into a running name is refused. Every refusal comes back
  as `Event::SnapshotRestoreFailed` and is logged; a restore that works is not reported, because the
  client is already leaving.
