# v0.45.1-nkmk.20

- **Upstream base:** unchanged — the `v0.45.1` release tag (`efd8fd5a8`)
- **Range:** `v0.45.1-nkmk.19..main`
- **Released:** 2026-09-11

Two patches, both finishing something the last release started. nkmk.19 taught a *resurrected*
command pane to drop to the shell when its command exited cleanly; the panes an operator actually
stares at come from the CLI, and they still held. A new config key extends that drop to every
command pane, with the old behaviour as the default. And the generated service unit now leads its
recorded `PATH` with the pin directory, so a pinned server resolves the pinned build by name
instead of the package one.

## Added

### `command_pane_on_clean_exit` — a command pane can drop to the shell

```
// config.kdl
command_pane_on_clean_exit "shell"

$ zellij run -- cargo test           # before: EXIT CODE: 0, and an ESC to reach the shell
                                     # now:    the shell, in the directory cargo ran in
```

nkmk.19 gave a resurrected pane that behaviour and stopped there. But `zellij run --` and
`zellij action new-pane -- cmd` — the same call an agent makes — still held on success and wanted
the same ESC. The new key extends the drop to all of them.

**Two values, and the default is the old behaviour.** `"hold"` is the default and is upstream:
every command pane holds on `EXIT CODE: 0` and waits for `<ENTER> run, <ESC> drop to shell,
<Ctrl-c> exit`. `"shell"` makes a clean exit take the ESC path itself, landing at a shell in the
directory the command ran in. An unknown value fails the config, as every other enum-valued
top-level key does.

**One global switch, and layout command panes come along.** A per-origin distinction would need a
field on `RunCommand`, the expensive shape nkmk.19 paid for once. So under `"shell"` a layout
`command` pane also drops, losing the ENTER-to-re-run its banner offered. That is the price of the
cheap surface, and it is the operator's to accept by setting the key.

**A resurrected pane is unconditional.** It still drops on its own under either value. `"hold"`
restores upstream behaviour for everything else and changes nothing about a pane that came back
with a session.

**A failure still holds, under both values.** Only `Some(0)` qualifies — a non-zero status prints
its code and waits, and a signal reports `None` and does the same.

**A suppressed pane is never dropped.** `Tab::drop_held_pane_to_shell` resolves its pane through
`get_pane_with_id_mut`, which also reaches the suppressed map — the scrollback-editor path, where a
pane stands aside for the editor that replaced it. nkmk.19 was safe there only because
`resurrected` is never set outside a resurrection layout; a config key any command pane can hit is
not. The decision now sits inside the tiled and floating branches of `Tab::hold_pane` and is
`false` in the suppressed branch, so a suppressed pane keeps its hold and the pane it stands in for
is restored.

**Nothing crosses a contract.** It is an `Options` field, and fork `Options` fields are absent from
the client/server protobuf and set to `None` in the `TryFrom`. No protobuf tag, no plugin API, no
snapshot format. The value is shared from `Screen` to every `Tab` as an `Rc<RefCell<…>>`, the way
`input_while_scrolled` is, so a config reload reaches every tab.

**The consumer sees nothing new.** A dropped pane lands exactly where ESC leaves one today:
`is_held` false, `exited` false, the pane running a shell. `list-panes --json` keeps its shape, and
every reader that already handles an ESC-dropped pane handles this one.

## Fixed

### The generated unit's `PATH` leads with the pin directory

A shell that carries a package prefix ahead of the pin directory recorded the pin directory behind
it. The unit then `exec`ed the pinned build while every `zellij` the **server** resolved by name —
a `zellij run --`, a `zellij edit`, a resurrected command — was the package one. Seen on a shell
whose `PATH` put the pin directory eighth.

The rule the unit generator follows splits, and the split is narrow:

- **The canonical `pin_exe` directory is hoisted to the front**, even when the installing `PATH`
  already names it further down. It is the per-user data directory zellij owns, and it holds
  zellij and nothing else — so the hoist changes which `zellij` the server resolves by name and
  changes nothing else at all.
- **Any other directory keeps its place.** A package prefix, a per-user bin, a directory an
  operator put where they wanted it: none of them moves, because moving one would change which
  build of *everything else* the server resolves.

A hoist is the only reordering. The pin directory's later occurrence is dropped by the same dedup
that drops any other repeat. Both generators take the value from one function, so the plist's
`PATH` inside `EnvironmentVariables` moves with the unit's.

It is still a **default**. A machine whose config states its own `PATH` — `launchd { env { PATH … }
}`, the launchd `keys` hatch, or `systemd { service "Environment=PATH=…" }` — is unaffected,
because none of those is generated.

## Operator notes

- **A unit enabled before this release carries the old order**, and nothing rewrites it in place.
  The drift check reports it, `session enable` re-records it, and then `session restart`, because a
  server keeps the `PATH` it was created with. Only a machine that pins its binary *and* whose
  shell names the pin directory somewhere other than first sees that drift; everywhere else the
  generated value is byte-identical and nothing is reported.
- **The shared config already seeds `command_pane_on_clean_exit "shell"`.** It is a top-level key,
  and an unknown top-level key is ignored rather than rejected, so it could be rolled out ahead of
  the binaries. A machine still on an older build ignores it and holds; a machine that has caught
  up drops.
- **Set `"hold"` to keep upstream behaviour.** Omitting the key does the same thing. Nothing else
  read from `config.kdl` changed meaning, and no existing fork option changed name, value, default
  or effect.
