# v0.45.0-nkmk.2

- **Upstream base:** `f42ca3c79` on upstream `main` (workspace version `0.45.0`) — unchanged from
  nkmk.1; upstream has landed nothing since
- **Range:** `6a93f47bd..main` (two feature patches, the plugin rebuild and the version bump)
- **Released:** 2026-08-10

Two additions, both aimed at driving zellij from a script or an agent: a bell notification that
survives a pass through the panes, and a pane identifier that a pane id cannot be mistaken for.

**Read the breaking-change section if you build plugins against this fork.**

## What changed in the fork

### A dwell before a focused pane's bell clears (`bell_clear_delay_ms`)

```kdl
bell_clear_delay_ms 1000
```

A pane that rings the bell shows `[!]` in its title until it is focused, and upstream clears that
the instant the pane takes focus. Cycling through panes to find the one that rang therefore erases
every notification on the way. With `bell_clear_delay_ms` set, the `[!]` clears only once the pane
has been focused, without interruption, for that many milliseconds — counted from the later of the
focus and the last ring. Flicking past a pane keeps its notification. A pane that rings again while
you sit on it restarts the dwell, so a new ring is never swallowed.

The dwell covers every way a pane takes focus, mouse clicks included; both focus paths now route
through the same decision.

Default is 0, which is upstream's behaviour to the byte: the focus paths clear the bell
synchronously, and no timer is involved.

Multiple clients count independently — any one of them dwelling on the pane is enough to clear it.

### A pane uuid that outlives id reuse

```
zellij action list-panes --all --json
```

Every pane — terminal and plugin — is given a v4 uuid when it is created, and reports it as `uuid`
in `list-panes --json` and in `PaneInfo`.

A pane id does not identify a pane on its own. It counts up from 0 per server, so the id a script
wrote down names a different pane in the next session, and after a restart or a resurrection of the
same session. Terminal and plugin ids are separate sequences, so pane 0 is two panes at once. A
uuid is handed out once, ever, which buys two things: re-targeting a pane you created without
matching on its title, and an existence check — if the uuid is no longer in the listing, the pane
is gone.

What the uuid promises, exactly:

- It is stable for the pane's whole life inside one running server. Renaming, moving between tiled
  and floating, stacking, suppressing and hiding all keep it.
- It does **not** survive a server restart, a session resurrection, or a snapshot restore. What
  comes back is a new pane with new state, and it says so with a new uuid.
- A pane read out of a saved layout reports an empty uuid, because it is a description of a pane
  rather than a pane. That is the defined answer, not a bug.

Note what the reuse this protects against is, and is not. Inside one running server the id counter
only climbs, so a closed pane's id is not reissued while that server lives. The reuse the uuid
guards is the reuse *across* servers and restarts, and the collision between the terminal and
plugin id namespaces.

## Breaking changes

**`event.proto` gained a field.** `PaneInfo` now carries `string uuid = 30`.

The addition is additive, so decoding is safe both ways: a plugin built against nkmk.1 keeps
working against this build and treats tag 30 as an unknown field. It simply never sees a uuid.
Rebuild against this release's `zellij-tile` to read the field. The fork's own bundled plugins are
rebuilt here.

The nkmk.1 requirement still stands on top of this: **anything not yet rebuilt since 0.44 must be
rebuilt**, because nkmk.1 renumbered the fork's plugin API tags. That is a wire-incompatible change,
unlike this one.

## Upstream

`git fetch upstream` at release time reports no commits past `f42ca3c79`. The base is the same tree
nkmk.1 shipped against, so this release carries no upstream changes.
